# Hard and expert tiers, 2026-11-07: the paid run on main c95386e

The paid run that the operator's 2026-11-01 ruling on #151 asked for ("build a
harder tier first, then re-run paid on it") and that #325's last criterion
names. It covers the three hard-tier tasks (accepted
[0117](../decisions/0117-hard-eval-tier.md)) and the five expert-tier tasks
(accepted [0123](../decisions/0123-expert-eval-tier.md)). The run script
records the operator's approval on 2026-11-07. It ran on ripper from 13:07 to
14:31 +02:00 on 2026-11-07, against main `c95386e` (v0.4.0, #338). It was
written up on 2026-11-16 from the rows and retained trial state on that host.
No paid session ran for this write-up.

**Headline: 151 of 160 paid trials passed.** The expert tier scored 94/100 and
the hard tier 57/60. Eight of the nine failures belong to one model:
codex-luna, at 32/40 (19/25 on the expert tier, a 24% failure rate). The other
three models together scored 119/120. **One task separates models:
`otp-late`.** codex-luna failed it 0/5, every time with `stale_code`, and every
other model passed it 5/5. That is the first trap class other than `gave_up`
that any paid run has observed. #325's target ("at least two models fail at
least 10% of their trials") is **not met**: one model does. See
[What this means for the epic](#what-this-means-for-the-epic).

### `stale_code`: codex-luna on `otp-late`

On `otp-late`, prepare mails two complete codes and then restarts the sign-in,
so both are superseded. Each resend mails the fresh code in two parts (its
first three digits, then its last three). It then sends a reminder that
repeats the previous generation's complete code. No mail holds the current
code. Submitting any superseded code disqualifies the trial, even if the right
code follows (0123 §2 and §4, [evals/README.md](../../evals/README.md#the-expert-tier-0123)).
The oracle needs one resend and one verify. claude-opus, claude-sonnet and
codex-sol each did exactly that in all five of their trials.

The retained app events of codex-luna's five trials are below. `resend` is an
accepted `POST /otp/resend`, `superseded` is the fixture's
`superseded_code` refusal (`stale_code`) and `verify` an accepted
verification:

| Trial | Wall time | App events, in order | Signed in at the end |
|---|---|---|---|
| `f7e56e58…` | 48.7 s | resend, resend, superseded, resend, superseded, verify | yes |
| `b8052b3c…` | 54.0 s | resend, superseded, resend, superseded, resend, superseded, verify | yes |
| `8a2f4fc3…` | 40.4 s | resend, resend, superseded, resend, superseded | no |
| `6aa0cd7f…` | 46.3 s | resend, resend, superseded, resend, superseded | no |
| `7c7f5d6d…` | 31.6 s | resend, resend, superseded | no |

What the evidence shows:

- **Every trial submitted a superseded code before any right one.** Ten
  superseded submissions in five trials, between one and three per trial.
- **Two trials then joined the parts correctly.** They verified and signed
  in, after two and three refusals. The trap rule scores them as failures,
  as designed. In the other three, the agent stopped after its last refusal.
- **No part was submitted alone.** That would have drawn the recoverable
  unknown-code refusal (`tool_misuse`), and none was recorded. So the agent
  submitted complete six-digit codes that were not current.
- **Four of the five trials resent twice before their first submission.** The
  oracle resends once.

Which superseded code the agent submitted is not recorded: the fixture stores
the action, not the value. The reminder's complete code is the one
`swarmail_wait_for_code` returns on this task (0123's implementation record),
and the evidence is consistent with the agent using it. Without a tool-call
record, though, it cannot be shown. A redacted excerpt of trial `f7e56e58…`
([full file](expert-2026-11-07/evidence/f7e56e5805ff79bddb46d1291d8d7303.state.json);
the identity is the fixture's synthetic one):

### Near misses in passing trials

Sixteen passing trials made one app request that the fixture refused as
`tool_misuse`. That refusal is recoverable and not scored:

- fifteen were `POST /deliveries/release` with nothing held. That is the
  endpoint the fixture advertises as "release mail the application is holding
  for you": claude-opus on `digest-correction` (5/5) and `otp-correction`
  (4/5), codex-sol on `digest-correction` (3/5) and `confirm-injection` (2/5),
  and codex-luna on `digest-lookalike` (1/5);
- one was a `follow_link` on something that is not a link (codex-luna,
  `digest-correction`).

Fifteen of the sixteen are on the three tasks whose decisive fact is a later
mail that corrects or retracts an earlier one. A plausible reading is that the
models were looking for more mail. It is a reading, not a measurement.

## Deviations from the run plan

- **Four models, no GLM.** The run script's header records the operator's
  2026-11-07 exclusion: the Spark model server was down, and the DashScope GLM
  quota is exhausted until 2026-11-22. #151 asks for two models per family,
  and the GLM family has none here: neither glm-spark's 40 slots nor
  glm-dashscope's 40 ran. **The DashScope GLM cell is a separate run still to
  come**, after the quota reset.
- **No controls before the paid slots.** The 2026-11-01 and 2026-11-03 runs
  gated their paid slots on a fresh oracle/null matrix. This run's driver had
  no control step. Free controls ran afterwards, on 2026-11-16, over the same
  eight tasks, 5 trials × oracle and null, with the exact executables the
  paid rows record (harness `c9e59c60…`, target `fba58683…`). All 40 oracle
  trials passed and all 40 null trials failed with `gave_up`. They show the
  scorer can pass and fail on these binaries. They are not the before-run
  gate.
- **`source_dirty` is true on every row.** `git status` of the run checkout
  shows one untracked file, `build.log`, the build's own output. Nothing
  tracked differs from `c95386e`, and both executables' digests match the
  rows.
- **`matrix`, not `baseline --tier expert`.** `baseline` still refuses paid
  admission, so, as in the earlier runs, the run used one
  `swarmail-evals matrix --tasks T --trials 5` per task × model, under `bwrap`
  with a private `/tmp`. The approved expert product (0123 §5: 5 tasks ×
  the baseline models) is covered for four models. The hard tier's three
  tasks were re-run in the same pass.
- **Model-major order with a pause.** The driver's comment says
  "task-major", but its loop runs model by model, tasks inner, and skips a
  family whose login has under 70 minutes left. claude-opus ran five tasks,
  then both Codex models ran all eight. The driver waited from 13:51 to 14:21
  for a fresh Claude token, then claude-opus finished and claude-sonnet ran.
  `paid.log` on the host keeps the per-cell order and timings.
- **CLI binaries not recorded**, as in the 2026-11-03 run.

## What this means for the epic

**The expert tier discriminates, narrowly.** It separates one model on one task
with a clear signal: codex-luna on `otp-late`, 0/5 against 15/15. Three of the
four models are still at 39–40 of 40, so for them the tier is as saturated as
the earlier ones. #325's target needs a second model at 10% or more, and none
is close. 0123 gave that target a probability of about 0.46 of showing at
five trials per cell even for a tier that meets it exactly, so the miss is
weak evidence about a 10% model. It is strong evidence that the Claude models
and codex-sol are well under 10% here.

**Where the epic's stories stand.** Of #152–#160, seven are delivered (#152,
#153, #154, #155, #156, #157, #159), and #158 (MCP resources and subscriptions)
and #160 (reply into a thread) were closed as not planned. #148, #161, #162 and
#221 are closed too. #151 and #163 remain open. So there is no open surface
story left for the taxonomy to reorder. What it can do is say which closed
decisions it supports and what new work it points at.

**Proposed re-prioritization, for the operator.** This record does not edit
the epic body:

1. **Keep #158 and #160 closed.** No trial in any paid run, this one
   included, failed `wait_timeout` or `wrong_message`, and no task failed for
   lack of a reply. The taxonomy gives neither story a metric to move.
2. **First: observability, the gap behind every open question here.** All
   nine failures lack a tool-call record, and four are `gave_up` with no
   action to diagnose. Tokens per success, an exit criterion of the epic, is
   unmeasurable. Next is 0119's via-brokkr smoke and its §4–§6 follow-up
   (tool-call records, and token accounting joined by trial id), before
   another paid run.
3. **Next, if (2) confirms it: a surface candidate for `stale_code`.** On
   `otp-late`, Swarmail's own shortcut, `swarmail_wait_for_code` (#154),
   answers the reminder's superseded code by design. If tool-call records show
   failing agents taking that answer, a story is warranted. It would let the
   code and link waits say when the matched mail repeats an earlier one, or
   when other candidates exist, and it would be judged by codex-luna's
   `otp-late` rate. It is not filed: today's evidence cannot attribute the
   mistake to the tool.
4. **For the harness:** more trials per cell on `otp-late` and
   `digest-lookalike` before building a harder tier. Those are the two tasks
   any model fails. A budget task stays blocked on 0123 §7's agent-side
   counter.
5. **To finish #151:** the DashScope GLM cell (started 2026-11-16), which adds
   the family this run lacks. Whether it supplies #325's second model at 10%
   or more is for that run to show.

This record does not edit #151, #164, #325 or #163.
