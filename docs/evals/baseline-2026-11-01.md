# Baseline, 2026-11-01: the eval suite on main a4f552d

The #151 paid baseline. The operator approved its cost on 2026-11-01. It ran
on ripper from 12:47 to 16:01 +02:00, against main `a4f552d` (#300).
The harness build and the target came from the same clean checkout.

**Headline: 395 of 400 paid trials passed.** Every task passed for four of the
five models measured, every time. The five failures all come from one model,
are all one class, and are spread across five different tasks. At this
difficulty **the suite does not discriminate between current models**, so its
failure taxonomy is too thin to re-prioritize #152–#160 on its own. See
[What this means for the epic](#what-this-means-for-the-epic).

## Failure taxonomy

| Class | Count | Where |
|---|---|---|
| `gave_up` | 5 | codex-luna only: signup, otp, entity-url, reset-login, sibling-addresses (one trial each) |
| every other class (`wait_timeout`, `wrong_message`, `wrong_link`, `stale_code`, `tool_misuse`, `budget`, `harness_error`) | 0 | — |

The five failures have the same shape. The agent exited with status 0 after
16.6–22.5 s, close to that model's passing times on the same tasks (medians
13.1–19.5 s). The fixture's retained state shows the mail delivered and
**no action against the application at all**: no confirmation, no login and
no event (for example `state.json` of trial `902c488b…`, signup). So the model
ended its session believing it had finished, or gave up early. It did not act
on a wrong message, link or code. Which of those it was cannot be told from
the retained evidence.

**Transcripts: not available.** The issue asks for three transcripts per
dominant class. The wrappers send raw CLI stdout and stderr to `/dev/null` on
every outcome, and there is no debug or redaction mode
([wrappers.md](../../evals/wrappers.md), "Raw CLI stdout/stderr go directly to
`/dev/null`"). The retained per-trial evidence is `state.json`, `result.json`,
`metadata.json` and `diagnostics.log`. It is kept in the run's output tree on
the operator's host, not in this repository. Capturing redacted transcripts
needs a wrapper change. It is listed under [Not measured](#not-measured).

## Deviations from the run plan

- **Five models, not six.** The DashScope route of `dashscope/glm-5.3`
  failed its authenticated smoke with HTTP 429 `insufficient_quota`: the
  token-plan monthly quota is exhausted until 2026-11-22 16:00 UTC. On
  2026-11-01 the operator ruled to run the five now and add the glm-dashscope
  cells after the reset. GLM is therefore represented by one model
  (`spark-glm/GLM-5.3-Flash-EXL3`), not the two per family the issue asks for.
- **`matrix`, not `baseline`.** `swarmail-evals baseline` refuses paid
  admission ("locally evidenced CLI/auth contracts are incomplete"). The paid
  product was therefore run as one `swarmail-evals matrix` per task × model
  (five trials each), in task-major order, with the same agent declarations,
  deadline and concurrency. The controls ran first as one oracle/null matrix
  over all 16 tasks, and their result gated the paid run.
- **Token freshness.** By design the wrappers forward an access token with no
  refresh token. Before each chunk the driver waited until the selected
  family's login had at least 70 minutes left, and it ran chunks of other
  families in the meantime. No chunk started on a token that could expire
  mid-trial.
- **A private root per run.** The whole run executed under `bwrap` with a
  user-owned tmpfs root and a private `/tmp`. The reason is that admission
  (`/tmp/swarmail-evals-<uid>/trial.lock`) is shared with the house evals
  tests on the same host, which would otherwise refuse each other. The host
  network was shared, as the providers need it. This is not trial isolation
  (#221): it separates the baseline from other processes on the host, not
  trials from each other.
- **Ordering against #152–#160.** The issue asks for a baseline *before* any
  #152–#160 change merges. That did not happen. Main `a4f552d` already
  carries #152–#157, #159 and #162, so this measures the improved surface,
  not the epic's starting point.

## What this means for the epic

The suite is **saturated** at this difficulty. Four models are at 80/80, and
the one failure class appears only as rare early exits by one model. A
taxonomy this thin cannot rank #152–#160 against each other: no failure points
at timeouts, wrong messages, decoy links, stale codes or tool misuse, which
are the classes those stories target. Two readings follow, and choosing
between them is the operator's call:

1. **The stories already did their job.** Main already carries most of
   #152–#160. A pre-epic baseline at the starting point (for example the
   commit before #152) would show what they bought. That needs the same paid
   run again on an older checkout.
2. **The tier is too easy to steer by.** Harder tasks (longer flows, more
   decoys, adversarial timing, several inboxes per agent) or harder budgets
   (tighter deadlines, token caps) would bring back failures to rank work by.
   That is #148/#163-shaped work, not a re-run.

Either way, the epic's re-prioritization criterion ("the stories below are
re-prioritized from its failure taxonomy") cannot be met from this data
alone, and this record does not edit the epic body.
