The agent loop

Clear, act, assert — no sleep-polling

Mail arrives, await returns. Links and OTP-like codes are extracted at ingest, so the assertion is a field read — not a regex over HTML.

agent-loop — swarmail
# 1 — start clean (per-test inbox: the AUTH username is the inbox)
$ curl -X DELETE localhost:8025/api/v1/inboxes/test-run/messages
# 2 — trigger the flow (signup, reset, invite, …)
# 3 — block until the mail arrives — push-based, subscribes before it checks
$ curl "localhost:8025/api/v1/inboxes/test-run/await?to=user@x.io&count=1&timeout_ms=5000"
{
  "matched": 1,
  "emails": [{ "subject": "Verify your account",
             "links": ["https://x.io/verify?token=…"],
             "codes": ["424242"] }]
}
# 4 — no regex over HTML. The fields are already there.
01 · isolate

Every parallel test or agent gets its own inbox for free — proj-42, test-run-7. The AUTH username is the inbox.

02 · wait

…/await long-poll and MCP swarmail_wait_for_email block until arrival. Subscribe-before-scan: nothing is missed while connecting.

03 · assert

links, codes, thread headers — extracted once at ingest (decision 0005), served as plain fields.

What's inside

Everything a test run needs, one static binary

The scratch container is about the size of the binary. No database to babysit, no Node runtime, no config file.

📮Lossless ingest

SMTP DATA inserts synchronously — a 250 means the mail is queryable and (with --data-file) on disk. No async gap where mail can vanish.

🧪Chaos on SMTP

Probability, error lines and delays injected at connect, mail from, rcpt and data — set it, run your retry tests, clear it.

🤖MCP, native

HTTP (Streamable JSON-RPC) and stdio transports. Agents close the loop on signup, reset and magic-link flows — no browser tab.

🪤MailHog / Mailpit shims

Point an existing MailHog or Mailpit client at the HTTP port and it works — the two shapes test suites actually hit, from one store.

🧵Threads + live UI

Conversations grouped by References/In-Reply-To chains with normalized-subject fallback; the SSE-driven inbox view updates itself.

🪝Webhooks

Queued, retried (100 ms → 1.6 s), inbox-filtered, http:// and https:// with a per-CA client cache — never blocking the SMTP path.

📥POP3

RFC 1939 core + TOP/CAPA on the same store. The maildrop is an inbox — mail delivered over SMTP reads back over POP3.

🔐STARTTLS

Real rustls upgrade, RFC 3207 session restart, bounded handshake deadline. Without a cert the plaintext listener stays byte-identical.

💾Persistence

--data-file commits every change to bundled SQLite (WAL, fsync-per-accept) and restores the full state before the server answers anything.

Failure paths

Break SMTP on purpose

Retry logic is code too — and it deserves a test. Inject failures at the protocol stage you care about, then clear chaos and prove recovery.

chaos — inject
$ curl -X PUT localhost:8025/api/v1/chaos \
    -H 'content-type: application/json' -d '{
      "data": { "probability": 30,
                "error": "451 4.3.0 tempfail",
                "delay_ms": 250 }
    }'
webhooks — subscribe
$ curl -X PUT localhost:8025/api/v1/webhooks \
    -H 'content-type: application/json' -d '[
      { "url": "http://127.0.0.1:9999/hooks",
        "inbox": null,
        "secret": "s3cret" }
    ]'

AI-native

Agents drive the mail, end to end

Twelve tools over MCP — search, get, seed, chaos, and swarmail_wait_for_email, which blocks until the mail actually arrives. Point Claude Code, Codex or Cursor at it and the agent closes its own loop.

.mcp.json
{
  "mcpServers": {
    "swarmail": { "type": "http", "url": "http://localhost:8025/mcp" }
  }
}

stdio too: {"command": "swarmail", "args": ["mcp"]} — the bridge speaks JSON-RPC over stdin/stdout.
