# v0.4.0 — DKIM, spam, link and DNS checks in the deliverability report

Fourth release, prepared 2026-11-06 on `main` at `7478073` (#336). It
carries everything merged since v0.3.0 (`8732445`, 2026-11-03): offline
DKIM verification, built-in spam signals, per-link findings with an opt-in
reachability probe, and a declared DNS policy in the deliverability
report; the MailSlurper shim's subject escaped the way MailSlurper escapes
it; parse admission, which brings in-memory ingest under concurrency down
to a fraction of its v0.3.0 CPU; the published paid run of the hard eval
tier, and a new expert tier.

The deliverability report is the one surface that changes for every
caller: its bytes, its `rule_set_id` and its schema move (see
*Upgrading*). Everything else new is opt-in or invisible on the wire.

The frozen guarantees are unchanged: an SMTP `250` means the mail is
queryable (0001), `await` subscribes before it checks (0002), pruning is
oldest-only (0003), and extraction happens at ingest (0005). Each entry below
names the decision that governs it, and every one of them is accepted.
The operator accepted the 0118 addendum (the MailSlurper subject) on
2026-11-05. On 2026-11-06 the operator accepted the three named holds of
0125 (DKIM): its dependency additions, its compiled-in but unreachable
resolver, and its one clock read as an amendment of accepted 0085 §8. Later
that day the operator accepted every decision still proposed, in full:
0119 (the eval recipe), 0120 (the DNS policy), 0121 (link checks), 0122
(spam signals), 0123 (the expert tier), 0124 (parse admission) and the rest
of 0125. Two of those acceptances came after the code had merged: #329 (0120)
and #328 (0121) merged on 2026-11-05, though each record had held its PR
for the operator; the acceptance legitimises both merges after the fact.

## Deliverability

The report at `GET /api/v1/messages/{id}/deliverability` and MCP
`swarmail_get_deliverability_report` gains four families of checks: the
three below and DKIM verification (next section). All of them are computed
lazily from the stored bytes, off the SMTP path, and cached as before; no
extraction moved and nothing runs at ingest. The report's `rule_set_id`
moves from `swarmail-html/3` to `swarmail-html/6`. `swarmail-spam/1`,
`swarmail-html/4` and `swarmail-html/5` were the ids on `main` between the
four merges; none shipped in a release. See the
[deliverability guide](../guide/deliverability.md) for every rule, bound
and known gap.

- **Built-in spam signals** (0122, #327, closes #260). Six
  offline, deterministic rules read only the captured message: the root
  Subject, the root From display name and the sender's `text/plain` bodies.
  There is no external scorer, network, clock, locale or configuration.
  - `spam.subject.all_caps.v1` (warning): eight or more ASCII letters,
    none lowercase;
  - `spam.subject.punctuation.v1` (info): `!!`, `??` or `$$`;
  - `spam.subject.phrases.v1` and `spam.body.phrases.v1` (warning): one of
    fourteen fixed high-pressure sales phrases, matched ASCII
    case-insensitively on word boundaries;
  - `spam.from.display_name_address.v1` (warning): an address in the From
    display name that is not the mailbox's own;
  - `spam.body.zero_width.v1` (info): three or more zero-width characters
    (ZWJ excluded) in a text part.

  Each rule emits at most one finding per report, never at error level.
  HTML is never scanned for phrases (HTML-only mail already gets
  `bulk.plain_text.v1`). Aggregate decoded `text/plain` is capped at
  4,194,304 bytes, summed before any rule matches; over the cap the whole
  report fails rather than reporting a truncated scan as clean.
  **No weight and no total ship.** 0122 §2, accepted with the rest of
  the record, amends 0085 to add a severity-derived weight per finding and
  a report total. That follow-up is authorized but not built, so the guide
  still labels the weights "not in the report". Each rule is proved with a passing and a failing fixture
  over real SMTP, REST and MCP in `tests/spam_rules.rs`.

- **Per-link findings** (0121, #328, closes #258). Every visible
  `<a href>` of the eligible HTML parts is checked, using #154's anchor walk
  and label rules:
  - `link.scheme.unsafe.v1` (error): `javascript`, `vbscript`, `data` or
    `file`;
  - `link.url.invalid.v1` (warning): empty or not absolute, including an
    unrendered `{{placeholder}}` (a `#fragment` never fires);
  - `link.scheme.http.v1` (warning): plain `http`, except to `localhost`,
    `*.localhost`, `127.0.0.0/8` or `::1`;
  - `link.shortener.v1` (warning): an exact-host match against the built-in
    `swarmail-shorteners/1` list of seventeen hosts, never a lookup;
  - `link.anchor-host-mismatch.v1` (warning): the visible label names a
    host and the target matches none of the hosts it names.

  A finding sits at `link {part_path, byte_offset}` when the offset is a
  true source offset, else at `mime_part {path}`; no offset is guessed. The
  default report fetches nothing.

- **An opt-in reachability probe** (0121, #328). Whether a link
  answers, and where its redirects end, takes the network, so it needs two
  explicit steps: the server is started with
  `--link-reachability public|loopback` (env `SWARMAIL_LINK_REACHABILITY`,
  default `off`), and the caller asks with
  `GET /api/v1/messages/{id}/deliverability?reachability=true`. On an `off`
  server that request is a `400` and opens no connection. SMTP, MCP, the
  message page, `assert` and `await` never probe.
  - The address policy is default-deny, pinned to the IANA special-purpose
    registries as read on 2026-11-04: `public` contacts only addresses it
    proves globally routable, every hop's resolved addresses are checked
    before the connect, and a URL with credentials is refused. `loopback`
    also contacts `127.0.0.0/8` and `::1`, which lets mail content cause
    `GET` requests to the host's local ports;
    [network posture](../guide/network-posture.md) says when to choose it.
  - It sends `GET` with a fixed User-Agent, reads status and headers only,
    and is bounded: 5 s per link across at most 5 redirects, 2 s per
    connect, 32 distinct targets per request, 4 at once, 2 probing requests
    per server.
  - Its findings (`link.redirect-chain.v1`, `link.reachability.v1`,
    `link.reachability.refused.v1`) are added to that one response and
    never cached or stored.

  Proved only against loopback listeners in `tests/link_reachability.rs`; no
  test touches the internet. **Status:** the probe ships in this release,
  off unless both steps are taken. 0121 §7 held it for the operator's
  acceptance, because a broad reading of 0085's rejected "policy
  networking" alternative could cover it, but #328 merged it on 2026-11-05.
  The operator accepted 0121 in full on 2026-11-06, after the merge; that
  narrows 0085's rejection and 0106 §1's "no runtime network access" to the
  deterministic evaluator, which stays network-free.

- **A declared DNS policy** (0120, #329, closes #253). Checks that
  need DNS answers (DKIM keys, SPF, DMARC) read a declared, offline TXT map,
  never the network, and every report records which one it used in a new,
  required `dns` member:
  `{source, policy:{txt:[{name,values}], tempfail:[name]}, lookups:[…]}`,
  with `source` one of `default`, `server` or `inbox`.
  - **A server map:** `serve --dns-policy FILE` (env
    `SWARMAIL_DNS_POLICY`), a JSON file of at most 8192 bytes. A bad file
    stops startup before any listener binds; there is no fallback.
  - **An inbox map:** `PUT /api/v1/inboxes/{inbox}/dns` with the same body
    replaces the server map for that inbox (no merge) and echoes
    `{"inbox","source","policy"}`; `DELETE` clears it idempotently. A
    declaration is bounded at 8192 bytes raw and canonical and 256 names
    and values; at most 4096 inboxes hold one (a `503` beyond, nothing
    evicted). Inbox declarations live in memory and are not persisted.
  - A name declared `tempfail` yields a `temp_fail` lookup, which is never
    clean: a report holding one qualifies at no `no_findings_at_or_above`
    threshold.
  - `--dns-resolver` (env `SWARMAIL_DNS_RESOLVER`) defaults to `declared`;
    `real` is refused at startup: real DNS is not supported, and #254
    moved the resolver 0120 promised to a later story.

  DKIM verification (below) is the first reader of the map: the key,
  ATPS and `_report` names it asks for are recorded in `lookups`, and a
  declared `tempfail` key now makes a signature unverifiable. SPF and DMARC
  (#255) will read it too. 0120 amends 0085 §1's literal report shape
  `{rule_set_id, findings}`. Its PR was held for the operator but merged on
  2026-11-05; the operator accepted 0120 on 2026-11-06, after the merge.

## DKIM verification (#254)

- **Offline DKIM verification** (0125, #336, closes #254). Every
  `DKIM-Signature` field of a stored message is verified inside the lazy
  report evaluator, after the `250`; nothing runs at ingest or on the
  accept path. `rsa-sha256` (keys of 1,024 to 8,192 bits) and
  `ed25519-sha256` are verified under `simple` and `relaxed`
  canonicalization, with the body hash, `l=` and `x=`; `rsa-sha1` is
  unsupported. Parsing, canonicalization and the cryptography are the
  `mail-auth` crate's, pinned at `=0.14.0`. Every rule that decides a
  verdict around it is Swarmail's.
  - **Keys come only from the declared DNS map** (0120). Declare
    `<selector>._domainkey.<domain>` with `serve --dns-policy` or
    `PUT /api/v1/inboxes/{inbox}/dns`. Every in-grammar name the verifier
    asks for is answered from that map and recorded in the report's
    `dns.lookups`: the key name, the RFC 6541 ATPS name when a verified
    signature carries `atps=`, and `_report._domainkey.<domain>` when a
    failing signature has `r=y`. A name outside 0120's grammar is never
    looked up and fails closed. A key declared `tempfail` gives
    `dkim.not_evaluated.v1`, and the report qualifies at no threshold.
  - **The resolver is compiled in but never reached.** `mail-auth` cannot
    be built without one. The cache adapter answers every name from the
    map, and the one authenticator has no name servers. The operator
    accepted this on 2026-11-06 (0125 §2).
  - **Signatures are judged at receipt time.** A signature is expired when
    its `x=` is at or before the second the message was received, so a
    stored message's verdict is a function of its bytes, its receipt time
    and the policy. `t=` in the future is not enforced; an `x=` at or before
    `t=` is malformed.
  - **The clock residual: the one exception to byte-identical reports.**
    `mail-auth` 0.14.0 compares `x=` with the host clock inside its
    verifier, and no public API takes a time. For a signature whose `x=` is
    after the receipt second (and after `t=`, when present), once the host
    clock passes that `x=`, every verdict the later checks could give it
    becomes `dkim.expired_since_receipt.v1`, a pass included, and its key and
    ATPS lookups drop out of `dns.lookups`. A clean report can begin to
    disqualify, and a report recomputed after cache eviction can differ
    from the cached one. The operator accepted this read on 2026-11-06 as
    an amendment of accepted 0085 §8 (0125 §8). Swarmail itself reads no
    clock; unsigned messages and every other DKIM verdict are clock-free.
    Keep a test fixture's `x=` far from the wall clock.
  - **Eighteen `dkim.*` findings**, each with a passing and a failing
    fixture, all listed with their causes in the
    [guide](../guide/deliverability.md#dkim-verification-swarmail-html6).
    A verified signature and an unsigned message emit nothing. Every
    outcome that leaves a signature unverified is an `error`; the one
    `warning` is a verified signature whose `l=` leaves body content
    unsigned (`dkim.body_length_partial.v1`). Findings sit at
    `header {name:"dkim-signature", occurrence:k}`. A message whose header
    and body boundary or `DKIM-Signature` count differs between `mail-auth`
    and Swarmail gets one `dkim.header_boundary_ambiguous.v1` and nothing
    else.
  - **Bounds:** at most 16 `DKIM-Signature` fields per message and 128
    names in any `h=` (past either, one `dkim.limits_exceeded.v1` and no
    lookup); at most four body hashes before a bound refuses, 16
    verifications and 48 looked-up names within the bounds.
  - **Version:** signed messages' report bytes change, so the
    `rule_set_id` is `swarmail-html/6`. DKIM adds no report member and
    no OpenAPI or MCP schema change; its names appear in `dns.lookups`.
  - **Dependencies:** `Cargo.lock` gains 58 packages. They include
    `aws-lc-rs` and `aws-lc-sys`, C crypto code compiled at build time, and
    `hickory-resolver`, compiled in and unreachable. `mail-auth` brings a
    second `mail-parser` (1.0.0) beside Swarmail's 0.11.9. Every added
    licence is already on the allowlist, so `deny.toml` changes only a
    comment; `native-tls` stays absent and `evals/Cargo.lock` is unchanged.
    This is the operator's one dependency widening for the authentication
    stories (epic #251, 2026-10-26), which #255 and #256 reuse. The
    operator accepted the additions on 2026-11-06 (0125 §9).
  - **Not there yet:** SPF, DMARC and From alignment are #255, so the bulk
    checklist's `bulk.*` authentication facts (DMARC policy, alignment,
    aligned DKIM-or-SPF) stay unknown, and their error-level
    `*.not_evaluated.v1` findings still disqualify every report at every
    threshold. Assert on `dkim.*` rule ids, not on a threshold.

## Compatibility — the MailSlurper service API

- **The subject is HTML-escaped, as MailSlurper serves it** (0118 addendum
  of 2026-11-04, accepted 2026-11-05, #332, closes #326). The first full
  Alkemio trial against v0.3.0 ran 160 of 162 test files green; all five
  failures compared `subject` with a string holding `&#34;` where the mail
  has `"`, and the same tests pass against MailSlurper. The item's
  `subject` on `GET /mail` and `GET /mail/{id}` is now escaped in one pass
  with Go's `html.EscapeString` set: `&` → `&amp;`, `<` → `&lt;`,
  `>` → `&gt;`, `"` → `&#34;`, `'` → `&#39;`. It is unconditional, as Go's
  is, so `&amp;` becomes `&amp;amp;`. Only the `"` mapping is observed; the
  other four are inferred from MailSlurper being Go. `body`, the addresses,
  `GET /mail/{id}/message`, the native API, the Mailpit and MailHog shims,
  search and storage keep the sender's subject as it was. A list page
  stays inside its 64 MiB cap, and escaped bytes count toward it.

## Ingest

- **Parse admission** (0124, #335, closes #333). In memory mode
  under concurrent SMTP, v0.3.0 spent several times the CPU of data-file
  mode, on the blocking pool's short-lived threads. Each ingest parse now
  takes a permit before it goes to the blocking pool. The permit width is
  `std::thread::available_parallelism()`, which reads the CPU affinity mask
  and the cgroup quota. The wait is asynchronous, and the permit is
  released before the commit. SMTP `DATA` and REST seed are gated; MCP
  seed is unchanged. There is no flag, environment variable or chart
  value, and `Store::insert` is untouched, so a `250` still follows the
  commit (0001).

  In memory, a 40-connection burst on 2 CPUs now takes 5.7 s of CPU where
  v0.3.0 took 28–37 s, and runs at about 585 mails/s where v0.3.0 ran at
  107–141. Measured after merge with the container bench that found the
  issue (posted on #333): the image `sha-187859a…` under `--cpus=2`,
  implicit TLS, one connection per mail, 2000 mails at 40 connections after
  200 sequential, three runs, against two v0.3.0 runs of 2026-11-05:

  | | v0.3.0 | v0.4.0 |
  |---|---|---|
  | in memory, burst CPU | 27.9 / 37.4 s | 5.7–5.8 s |
  | in memory, burst throughput | 141 / 107 mails/s | 580–588 mails/s |
  | in memory, burst p50 / p95 send | 278–385 / 584–679 ms | 67 / 90–94 ms |
  | data file, burst CPU | 7.4 / 6.9 s | 4.9–5.0 s |
  | data file, burst throughput | 264 / 278 mails/s | 310–319 mails/s |

  Sequential cost, memory use and stored counts did not change; every run
  stored all 2200 mails. The issue's first measurement put v0.3.0's
  in-memory burst at 23.7–37.4 s and 107–166 mails/s over three runs. The
  bench scripts are the dispatcher's, not in the tree (see #333).
  `tests/ingest_cpu.rs` guards the relation in CI: over real SMTP, in-memory
  CPU per mail stays within 1.25× the data file's. The cause's detector is
  the parse-gate tests in `src/store.rs`, `src/smtp.rs` and `src/api.rs`.

  [`docs/evals/hard-2026-11-03.md`](../evals/hard-2026-11-03.md) publishes

- **An expert tier** (0123, #330, closes #325). The operator's
  answer to that run was "make it harder". Five tasks over four trap
  families, built so that no single read passes:
  - `otp-correction` and `digest-correction` (state across mails);
  - `otp-late` (timing);
  - `confirm-attachment` (format and content: the valid link is only in
    an attachment);
  - `confirm-injection` (instructions inside mail).

  Every task needs at least two reads, and acting on the first match, the
  newest match or a Swarmail shortcut tool's answer fails on some seed.
  Each records its trap, targeted mistake and expected failure class.
  `swarmail_evals::tasks::EXPERT_DIFFICULTY` holds an unpaid difficulty
  proxy per task (the oracle's tool calls and app requests, and the
  minimum reads), pinned by a test. The catalogue now lists 24 tasks: the
  default and hard tiers keep every byte. `matrix --tier expert` and
  `baseline --tier expert` select the tier; the latter is a separate
  5-task, 10-control, 150-paid-slot product. The budget and
  several-identities families are not built; 0123 §7 says why. Delivery
  ran free controls only: the oracle passes and the null agent fails on
  every fixed seed. See

## Upgrading from v0.3.0

The deliverability report changes for every caller; nothing else breaks on
the wire, the command line, the data file, the image or the chart. Checked
against the `v0.3.0` tag's code:

- **Report bytes change.** Every report's `rule_set_id` is
  `swarmail-html/6` (was `swarmail-html/3`), every report carries the new
  `dns` member after `findings`, and mail that had no spam, link or DKIM
  findings can now have some. A signed message whose key is not declared
  gets `dkim.key_missing.v1`, an error. A test that pins a whole report,
  its `rule_set_id` or a finding count must be updated.
- **A DKIM verdict can change after the fact.** For a signature whose
  `x=` lies after its receipt, a report computed once the host clock
  passes that `x=` reads `dkim.expired_since_receipt.v1` (accepted 0125
  §8). Every other report is still byte-identical for the same bytes and
  configuration.
- **Report schemas are closed and gain a required member.** OpenAPI's
  `DeliverabilityReport` and the MCP tool's `outputSchema` (MCP
  `2025-06-18` and `2025-11-25`) both set `additionalProperties: false`
  and now require `dns`. A client that validates a report against the
  v0.3.0 schema rejects a v0.4.0 report; take the new schema from
  `/openapi.json` or `tools/list`.
- **Report predicates.** `no_findings_at_or_above` reads severity only;
  weights do not exist. In production every message still carries the
  error-level `*.not_evaluated.v1` authentication findings, so no message
  qualified at any threshold in v0.3.0 and none does now. A `temp_fail`
  lookup also disqualifies: a DKIM key declared `tempfail` now produces
  one.
- **A new analysis failure.** A message with more than 4 MiB of decoded
  eligible `text/plain`, which v0.3.0 reported on, now fails analysis:
  REST `503 deliverability analysis failed`, MCP `isError`, and an
  `assert` or `await` that needs its report aborts.
- **A new endpoint.** `PUT` and `DELETE /api/v1/inboxes/{inbox}/dns`,
  behind the HTTP plane's Host/Origin guard like every route. Nothing
  existing was renamed or removed.
- **New flags, all off or neutral by default:** `--dns-policy`
  (`SWARMAIL_DNS_POLICY`, unset means the empty default map),
  `--dns-resolver` (`SWARMAIL_DNS_RESOLVER`, `declared`; `real` is
  refused) and `--link-reachability` (`SWARMAIL_LINK_REACHABILITY`, `off`).
  `GET …/deliverability` admits one query key, `reachability`; any other key
  is still a `400`, and `reachability=false` is the default report.
- **MailSlurper consumers** see escaped subjects (`"` as `&#34;` and the
  rest of Go's set). That is the fix; a consumer that compared the raw
  subject through the shim must compare the escaped form, as it would
  against MailSlurper.
- **Ingest.** No wire change. Under more concurrent sessions than usable
  cores, the extra parses wait for a permit instead of competing for the
  CPU; the `250` still follows the commit.
- **Data files** are unchanged: no column or table was added, so a v0.3.0
  data file opens as it is. Inbox DNS declarations are not written to it.
- **The MCP surface** is the same eighteen tools.
  `swarmail_get_deliverability_report`'s modern description and output
  schema name the new rules and the `dns` member; the `2025-03-26`
  descriptor keeps its historical text.
- **The startup log line** is unchanged.
- **Building from a checkout** compiles C code for `aws-lc-sys`, so it needs
  a C compiler; the published image and chart need nothing new. The
  dependency tree grows by 58 packages, all under licences the allowlist
  already held.
- **Rust callers of the library** (the crate is not on crates.io): `Config`
  gained `dns_policy` and `link_reachability`, `ServeArgs` gained those and
  `dns_resolver`, and `deliverability::Report` gained `dns`. Code that
  builds a `Config` with a struct literal must add `dns_policy: None` and
  `link_reachability: LinkReachability::Off`.
- **Eval harness users:** `swarmail-evals tasks` now lists 24 tasks, so a
  digest over the whole catalogue moves again (from `5b312d98…` to
  `a05c85d3…`). The default-tier subset (`6068b687…`) and the
  default-plus-hard subset (`5b312d98…`) are unchanged, and bare `baseline`
  plans the same 16-task product. `--tier expert` is new and optional.

## Known limits

- **DKIM is verified; SPF and DMARC are not.** DKIM signatures are
  verified offline against declared keys, but the bulk checklist's DMARC
  policy, From alignment and aligned DKIM-or-SPF facts stay unknown until
  #255 (SPF, DMARC, alignment), which is in delivery and not part of this
  release, and #256 (ARC). Their error-level
  `*.not_evaluated.v1` findings mean that in production
  `no_findings_at_or_above` qualifies no message at any threshold. The
  rules are dated heuristics, not client or provider measurements; empty
  findings certify neither compatibility nor deliverability.
- **DKIM's clock residual and interop gaps.** The one host-clock read is
  bounded as above and is one-way unless the clock is set back. No real DNS
  is supported: undeclared keys are `dkim.key_missing.v1`. `mail-auth`
  counts `l=` in raw bytes where RFC 6376 counts canonicalized ones, so a
  conformant signer whose two prefixes differ fails as
  `dkim.body_hash_mismatch.v1`. A `p=` that is base64 but not a key reads as
  `dkim.signature_mismatch.v1`, not `dkim.key_invalid.v1`. The resolver is
  unreachable, not absent. The Alpine and macOS `aws-lc-sys` builds are
  proved by CI, not locally.
- **Spam signals carry no weight or total.** Both wait for the operator's
  ruling on 0122 §2; the rules are a fixed English phrase list and a few
  structural signals, with the false negatives and positives the guide
  lists.
- **Link checks have no public-suffix list**, so a label naming a shared
  suffix (`github.io`) lets any subdomain pass, and names like `Node.js`
  can warn. Internationalized names are skipped, not compared.
- **The reachability probe uses the operating system's resolver**, whose
  lookup cannot be cancelled: a probe dropped at its 5 s budget leaves its
  lookup running until the resolver gives up. A special-purpose block that
  IANA allocates inside `2000::/3` after 2026-11-04 is contacted until the
  pinned table is edited. The probed response is never cached, so two
  probes can differ.
- **Inbox DNS declarations are process-local.** They are lost on restart
  and wake no waiter when they change. The chart has no value that mounts
  a `--dns-policy` file; use the per-inbox `PUT` there.
- **Parse admission has no knob.** Its width is the usable core count, so
  on one core parses run one at a time. The v0.4.0 figures above come from
  the dispatcher's container bench, not from a script in the tree; CI
  guards only the in-memory-to-data-file relation.
- **The expert tier has no paid run.** Whether current models fail it, the
  issue's target of at least two models failing at least 10% of trials, is
  unmeasured; `baseline --tier expert` is the operator's. The hard tier's
  paid run went 74/75 and does not discriminate, and the default tier's
  2026-11-01 baseline is saturated.
- **Eval trials are sequential.** One trial per uid runs at a time (0076);
  `--concurrency` other than 1 refuses. Trial isolation (0115) is
  prepared, not activated: it needs Linux and `/usr/bin/bwrap` 0.11.1 or
  later, and `--isolated` refuses every wrapper profile until the operator
  rules on provider egress.
- **Tokens per success are not yet measured.** Paid rows carry no token,
  turn or cost field and no transcripts. The eval recipe (0119, accepted)
  lands the journal join but measures nothing yet: `--via-brokkr` refuses
  until the driver invocation and accounting channel are observed and
  recorded, the value-bearing evidence mode 0119 §4 authorizes is not
  built, and `swarmail-evals baseline` still refuses paid admission.
- **The MailSlurper shim is a global mailbox.** Its clients see and wipe
  every inbox; isolation is one swarmail per suite. Of the subject
  escapes, only `"` → `&#34;` is observed upstream. The recalled details
  of 0118 §7 (the `pageNumber` spelling, the `/message` content type, the
  search keys, the plain-text delete answer and the past-the-end `404`)
  are still unread from source, and order and `dateSent` are receive time
  in UTC where upstream uses the `Date` header in local time.
- **The chart does not expose the MailSlurper port.** Enable the listener
  through `config` and publish port 4437 with a Service of your own.
- **Implicit TLS is one mode per process.** A listener serves STARTTLS or
  implicit TLS, never both. POP3 has no TLS.
- **MCP client compatibility receipts are still owed.** Recorded results
  from Claude Code, Codex, MCP Inspector and Claude Desktop remain
  operator-owned obligations under 0079.
- **Client packages are unpublished.** Neither npm nor PyPI carries them
  (0113).
- **The fair mail comparison has no result.** Only raw measurement is
  admitted ([`docs/evals/README.md`](../evals/README.md)).
- **Not on crates.io.** The crate is publish-ready; nothing uploads it.
- **No MCP resources or subscriptions** (0114); `resources/*` calls answer
  `-32601`.
- **Publication is not one transaction.** The image publishes before the
  chart, each guarded against a republish, and a chart failure after the
  image pushed leaves the image published (0019, 0051). The v0.3.0 tag's
  release run published both on 2026-11-03; this tag's publication is
  collected from its own release run.

docker run --rm --stop-timeout 30 -p 127.0.0.1:1025:1025 -p 127.0.0.1:1110:1110 -p 127.0.0.1:8025:8025 \
  ghcr.io/feedback-loop-ai/swarmail:0.4.0
