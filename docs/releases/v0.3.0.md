# v0.3.0 — drop-in for MailSlurper senders and readers

Third release, prepared 2026-11-03 on `main` at `e568a52` (#321). It
carries everything merged since v0.2.0 (`5645bd9`, 2026-11-02): implicit-TLS
SMTP, a MailSlurper service-API shim, a hard eval tier, the eval recipe on
brokkr, the eval flakes made deterministic (with one more race fixed after
them), and the published-chart install docs. Both new server features are
off unless you turn them on; an unconfigured v0.3.0 server behaves on every
port as v0.2.0 did.

The frozen guarantees are unchanged: an SMTP `250` means the mail is
queryable (0001), `await` subscribes before it checks (0002), pruning is
oldest-only (0003), and extraction happens at ingest (0005). Each entry below
names the decision that governs it. Of the four new records, the operator
accepted 0116 (implicit TLS), 0117 (the hard tier) and 0118 (the MailSlurper
shim) on 2026-11-02; 0119 (the eval recipe) is still a proposal.

## Mail plane

- **Implicit-TLS SMTP (SMTPS)** (0116, #317). `--smtp-implicit-tls` (env
  `SWARMAIL_SMTP_IMPLICIT_TLS=true`) makes the SMTP listener at
  `--smtp-listen` speak TLS from the first byte (RFC 8314 §3.3), so a sender
  configured as `smtps://` with legacy SSL — Ory Kratos' courier with
  `legacy_ssl=true`, for example — switches to swarmail by changing only its
  host. It is a mode of the existing listener, not a second one:
  - it reuses `--tls-cert` / `--tls-key` and refuses to start without the
    pair (`--smtp-implicit-tls requires --tls-cert and --tls-key`), before
    anything binds, so a port asked to be TLS never serves plaintext;
  - `--tls-handshake-timeout-ms` (default 10 s) now bounds any SMTP TLS
    handshake, implicit or STARTTLS, and the handshake runs inside the
    capped session task, never in the accept loop;
  - the `220` greeting is sent inside TLS, `STARTTLS` is not advertised and
    is answered `554 5.5.1 TLS already active`, and a plaintext client on the
    port gets no SMTP reply, at most a TLS alert and the close;
  - AUTH-named inboxes (0004), `--route-domain` routing (0112), `await`,
    extraction and accept-is-stored run the same code as over plaintext;
  - a `Connect` chaos rule is checked after the handshake, so an injected
    error line travels inside TLS.

  Proved over a real TLS client in `tests/starttls.rs`: delivery to the
  AUTH-named inbox, a stalled handshake dropped at the deadline, a plaintext
  client refused, and STARTTLS absent inside the TLS session. See
  [`docs/guide/smtp.md`](../guide/smtp.md#implicit-tls-smtps). On the chart,
  mount the pair with `tls.enabled` / `tls.secretName` and set
  `config: {SWARMAIL_SMTP_IMPLICIT_TLS: "true"}`.

## Compatibility — the MailSlurper service API

- **A MailSlurper shim on an opt-in listener** (0118, #320).
  `--mailslurper-listen <host:port>` (env `SWARMAIL_MAILSLURPER_LISTEN`) has
  no default: unset means no socket and no route. When set, it serves
  MailSlurper's service API at the root of its own port, so a suite that
  reads and clears mail through MailSlurper (Alkemio's `@alkemio/tests-lib`,
  for example) changes only its `MAIL_SLURPER_ENDPOINT`:
  - `GET /mail` answers `{"mailItems":[…],"totalPages":n,"totalRecords":n}`,
    newest first, 50 to a page (upstream's own size) with `?pageNumber=`;
    `mailItems` is omitted whenever the page is empty, so an empty store is
    exactly `{"totalPages":0,"totalRecords":0}`;
  - `GET /mail/{id}`, `GET /mail/{id}/message` (the item's body as
    `text/html`, sandboxed by `Content-Security-Policy: sandbox`) and
    `GET /mailcount` are served;
  - `DELETE /mail` with the exact JSON body `{"pruneCode":"all"}` wipes;
    MailSlurper's age-based codes `60plus`, `30plus` and `2wksplus` are
    refused by name, and any other body, content type or query key is a
    `400` that deletes nothing;
  - each item carries `id`, `dateSent` (the receive time as
    `YYYY-MM-DD HH:MM:SS` UTC), `fromAddress`, `toAddresses` (the envelope
    recipients, bare), `ccAddresses`, `subject`, `body` (the stored HTML,
    else the text, as decoded at ingest, so an `href`-only link stays
    literal) and `attachments` (always `[]`).

  The listener sits behind the HTTP plane's own Host/Origin guard, keyed to
  its own port, and speaks plain HTTP: terminate TLS at your ingress. The
  HTTP port serves none of these routes under any prefix. Every route is
  pinned on the wire in `tests/mailslurper.rs`; the known differences are
  listed in [`docs/guide/compat-shims.md`](../guide/compat-shims.md#mailslurper-service-api).

  **It is a global view, and its wipe clears every inbox.** MailSlurper has
  one mailbox, so the shim has no inbox selector: `GET /mail` and
  `GET /mailcount` read every inbox, and `DELETE /mail` with
  `{"pruneCode":"all"}` clears every inbox on the server, not only the
  ones its client wrote. Enabling the listener collapses per-inbox isolation
  (0004, 0112) for its clients. Run one swarmail (one process, one data
  file) per suite that uses the MailSlurper API. Swarmail's own
  `DELETE /api/v1/delete-all` remains the HTTP plane's only cross-inbox
  wipe; this is a second spelling of the same store operation, reached only
  when an operator enables the listener.

## Evals

- **A hard tier** (0117, #319). The v2 catalogue gains a `hard` tier of
  three tasks, each built on a mistake real agents make and each with a
  named trap that disqualifies the trial: `otp-backlog` (`stale_code`:
  twelve code mails out of order, only the body says which is current),
  `recipient-crowd` (`wrong_message`: five identical confirmations, only
  the exact recipient is right) and `digest-lookalike` (`wrong_link`: two
  anchors with one title, one on a look-alike host). The catalogue now
  lists 19 tasks: the 16 default-tier tasks keep their ids, fields and the
  baseline's catalogue digest (`6068b687…` for that subset). `matrix --tier`
  and `baseline --tier` select one tier, exclusive with `--tasks`; bare
  `baseline` still plans the operator-approved 16-task product, and
  `baseline --tier hard` is a separate 3-task, 90-paid-slot product. Every
  hard task passes with the oracle and fails with the null agent on fixed
  seeds; delivery ran free controls only. See
  [`evals/README.md`](../../evals/README.md#the-hard-tier-proposed-0117).
- **The flaky eval tests are deterministic** (#318, closes #302). The
  three tests that stopped verify on unrelated delivery runs under load
  now wait on real signals, with every assertion kept and no retries or
  longer sleeps:
  `cleanup_observation_error_and_forced_expiry_fail_with_live_owned_processes`
  (an injected fault no longer crosses owned groups through one global
  slot), `child_output_server_death_remains_a_harness_error_on_linux` (the
  helper reports its own exit instead of dying by TERM), and the
  digest-forty case of
  `focused_tools_complete_link_and_code_traps_without_guessing`, which was
  a seeded 1-in-40 collision in the test data, not a product miss: the
  zero-timeout wait was right, and 0001, 0002 and 0005 held.
- **One more eval test race fixed** (#321).
  `survivors_names_a_live_process_and_is_empty_once_it_is_gone`
  (`evals/tests/trial_isolation.rs`) read `/proc/<pid>/cmdline` as soon as
  `spawn` returned, before the child had exec'd, and once found it empty on
  CI. It now waits, with the suite's bounded `eventually`, until the
  cmdline shows the program, and keeps every assertion.
- **The eval recipe on brokkr, as measuring machinery** (0119, #316,
  refs #148). `.brokkr/recipes/eval/` runs a trial as a brokkr run: a
  `trial` exec seat runs `swarmail-evals trial` from a request the matrix
  wrote, and a `review` exec gate (the recipe's protected review) re-applies
  the task's check to the retained app state and is agreed with the row by
  a precedence table, never rewritten. `matrix --brokkr` runs each slot as
  one `brokkr run --recipe eval` with 0076's one-row-per-slot accounting;
  `report --journal` joins a typed journal-facts file
  (`evals/scripts/journal-facts.sh`) to the unchanged rows by trial id, with
  tokens, turns, wall time, deadline kills and tool calls each typed present
  or unavailable — never a bare `0` — and `tokens_per_success` `null` with
  a reason whenever a group's join is partial. `--evidence-dir` retains a
  structural per-trial tool-call record (names, classes, lengths and
  digests, no argument or result bytes, accepted 0075 §4). It lands the
  machinery and **measures nothing yet**: `--via-brokkr` refuses with
  `driver_contract_unknown`, paid agents are unsupported under
  `matrix --brokkr`, and only the oracle and null controls ran, through an
  offline stand-in for `brokkr run`. See
  [`evals/README.md`](../../evals/README.md).

## Upgrading from v0.2.0

There are no breaking changes on the wire, the command line, the data file,
the image or the chart. Checked against the `v0.2.0` tag's code:

- **Both new features are opt-in.** Without `--smtp-implicit-tls` the SMTP
  listener is byte-identical to v0.2.0's, STARTTLS included; without
  `--mailslurper-listen` no socket opens and the HTTP plane serves no new
  route (`GET /mail` there is still a `404`). No flag, environment
  variable, route, MCP tool or metric was renamed or removed, and the MCP
  surface is the same eighteen tools.
- **`--tls-handshake-timeout-ms`** keeps its default and its STARTTLS
  meaning; it also bounds the implicit handshake when that mode is on.
- **Data files** are unchanged: no column or table was added, so a v0.2.0
  data file opens as it is.
- **The startup log line** gains a `mailslurper` field (`None` when the
  listener is off).
- **Rust callers of the library** (the crate is not on crates.io): the
  public structs gained fields — `Config::mailslurper_listen`,
  `SmtpConfig::implicit_tls` and `RunningServer::mailslurper_addr`. Code that
  builds a `Config` with a struct literal must add
  `mailslurper_listen: None`; `SmtpConfig` built with
  `..SmtpConfig::default()` needs no change.
- **Eval harness users:** `swarmail-evals tasks` now lists 19 tasks, so a
  digest taken over the whole catalogue moves (to `5b312d98…`); the
  default-tier subset and bare `baseline` are unchanged. `matrix` still
  requires `--tasks` unless `--tier` is given. `matrix --brokkr`,
  `report --journal` and `--evidence-dir` are new and optional; result rows
  and the direct `matrix` path, the paid route, are unchanged.

## Known limits

- **The hard tier has no paid run yet.** Delivery ran the free oracle and
  null controls only; whether current models fail its tasks some of the
  time, as designed, is unmeasured. The paid run (`baseline --tier hard`)
  is the operator's. Until it exists, the 2026-11-01 baseline remains the
  only paid result, and its 16-task suite is saturated: four of five models
  scored 80/80, so it ranks nothing.
- **Eval trials are sequential.** One trial per uid runs at a time (0076);
  `--concurrency` other than 1 refuses. Trial isolation (0115) is prepared,
  not activated: it needs Linux and `/usr/bin/bwrap` 0.11.1 or later (stock
  Ubuntu 24.04 ships 0.9.0, which it refuses) with a host policy that lets
  bubblewrap create user, PID, network and IPC namespaces; macOS refuses by
  name. Until the operator rules on provider egress, `--isolated` refuses
  every wrapper profile, so no real model runs isolated, and its live
  criteria have not all passed.
- **Tokens per success are not yet measured.** Baseline rows carry no token,
  turn or cost field, and no transcripts were captured. The eval recipe
  (0119) lands the journal join and structural tool-call records but
  measures nothing yet: closing the gap needs the operator's first engine
  run, an authenticated via-brokkr smoke per agent family, a follow-up that
  forwards the observed accounting channel (0119 §6, awaiting the
  operator), and then a paid run. Value-bearing tool-call records wait for
  0119 §4's acceptance. The glm-dashscope cells and a pre-epic starting
  point were not run, and `swarmail-evals baseline` still refuses paid
  admission.
- **The three #302 eval flakes are fixed** (#318), each repeated under CPU
  load before merge, and the trial-isolation race found after them is fixed
  too (#321). That is not a claim that the eval suite has no other
  timing race; a new one is a new issue.
- **The MailSlurper shim is a global mailbox.** Its clients see and wipe
  every inbox on the server; isolation is one swarmail per suite. The
  shapes its consumer reads (`mailItems`, `totalRecords`, `subject`, `body`,
  `toAddresses`, and the empty-page omission) come from the operator's
  description of that consumer. Some upstream details are still recalled,
  not read from source: the `pageNumber` spelling, the `/message` content
  type, the search-key names, the plain-text delete answer and upstream's
  past-the-end `404` (0118 §7). Order and `dateSent` are receive time in
  UTC, where upstream uses the `Date` header in local time, so once more
  than 50 mails are stored the two can put different mail on page 1.
  Responses are never compressed.
- **The chart does not expose the MailSlurper port.** Enable the listener
  through `config` and publish port 4437 with a Service of your own; with
  `networkPolicy.enabled` the chart's policy does not admit it either.
- **Implicit TLS is one mode per process.** A listener serves STARTTLS or
  implicit TLS, never both; a deployment that needs both runs two servers,
  which are two stores. At the session cap an implicit-TLS client gets the
  unchanged plaintext `421` (0027 §3) and sees a failed handshake. POP3 has
  no TLS.
- **MCP client compatibility receipts are still owed.** Version negotiation
  is claimed, full revision conformance is not; recorded results from Claude
  Code, Codex, MCP Inspector and Claude Desktop remain operator-owned
  obligations under 0079. The agent setup guide's snippets are proved
  against the binary, not loaded by those clients, and the guide has not been
  run against a real model.
- **Deliverability reports do not verify authentication.** DMARC policy,
  From alignment and aligned DKIM/SPF are reported as error-level
  `*.not_evaluated.v1` findings until trusted observations exist (#253,
  #255), so in production `no_findings_at_or_above` qualifies no message at
  any threshold. The HTML rules are dated heuristics, not client
  measurements; empty findings certify neither compatibility nor
  deliverability.
- **Client packages are unpublished.** Neither npm nor PyPI carries them,
  their JavaScript/Python coverage is not measured and the packaged forms are
  unproved (0113).
- **The fair mail comparison has no result.** Only raw measurement is
  admitted ([`docs/evals/README.md`](../evals/README.md)).
- **Not on crates.io.** The crate is publish-ready; nothing uploads it.
- **No MCP resources or subscriptions.** They were evaluated and not
  shipped (0114); `resources/*` calls answer `-32601`.
- **Publication is not one transaction.** The image publishes before the
  chart, each guarded against a republish, and a chart failure after the
  image pushed leaves the image published (0019, 0051). The v0.2.0 tag's
  release run published both on 2026-11-02; this tag's publication is
  collected from its own release run.

## Try it

```bash
docker run --rm --stop-timeout 30 -p 127.0.0.1:1025:1025 -p 127.0.0.1:1110:1110 -p 127.0.0.1:8025:8025 \
  ghcr.io/feedback-loop-ai/swarmail:0.3.0
# or, from a checkout (the crate is not on crates.io)
cargo install --locked --path . && swarmail serve
```

`:0.3.0` and `:v0.3.0` exist once the signed `v0.3.0` tag's release run
has published them; until then use `:0.2.0`, `:main` or a checkout. The
chart is `oci://ghcr.io/feedback-loop-ai/charts/swarmail` version `0.3.0`
under the same condition.

evaluated, still are not (#255).
