# v0.2.0 — built for a program waiting on mail

Second release, prepared 2026-11-02 on `main` at `c336c95` (#308). It
carries everything merged since v0.1.0 (`01ee9b0`, 2026-10-07): the mail
plane that landed just after that tag (POP3, STARTTLS, persistence, the
MailHog/Mailpit shims, HTTPS webhooks, the Helm chart), the four
"Unreleased" sections recorded in [`v0.1.0.md`](v0.1.0.md), a wider MCP
surface for agents, focused waits, compact reads, attachments, recipient
routing, deliverability reports, client fixtures, an agent setup guide and
the eval harness with its first published baseline.

The frozen guarantees are unchanged: an SMTP `250` means the mail is
queryable (0001), `await` subscribes before it checks (0002), pruning is
oldest-only (0003), and extraction happens at ingest (0005). Each entry below
names the decision that governs it; several of them were proposals when this
note was written and are accepted, or not, by the operator in their own
records.

## Mail plane, storage and deployment

None of these was in the v0.1.0 artifact. Each landed after its tag and
ships for the first time here.

- **POP3** on `127.0.0.1:1110` (RFC 1939 core plus `TOP` and `CAPA`): `USER`
  names an inbox, the maildrop is a snapshot taken at `PASS`, and octet
  counts are what the client keeps (0028, 0037, 0046).
- **STARTTLS** with `--tls-cert` / `--tls-key` (rustls), and
  `swarmail gen-cert` to mint a self-signed pair for dev and test (0026,
  0034).
- **Persistence**: `--data-file` / `SWARMAIL_DATA_FILE` commits every
  insert, delete and clear to bundled SQLite before the `250` and restores
  the whole state on start. One server per data file, enforced by a lock
  (0033, 0042, 0047).
- **MailHog and Mailpit API shims** on the HTTP port, over the same store
  (0011, 0044, 0049, 0061).
- **Threads and a live-updating UI** inbox view.
- **HTTPS webhook targets** with an optional `ca_pem`, redirects never
  followed, deliveries dialed directly, CA work off the async workers
  (0041, 0048, 0067, 0068, 0069, 0077, 0078).
- **The Helm chart** (0008, 0026, 0051), verified in CI and published from
  release tags after the image.
- **Bounded sessions**: at most `--max-sessions` (default 256) concurrent
  sessions per SMTP and POP3 listener, the next answered `421`; listeners
  survive accept failures and `/healthz` reports a degraded one (0027,
  0036).
- **A loopback plane**: every listener binds loopback by default, the HTTP
  plane checks `Host` and `Origin`, and off loopback a present `Origin` must
  match the `Host` (0030, 0043). The image and chart bind `0.0.0.0`
  explicitly.

## Agent layer — MCP

- **Eighteen tools** over HTTP (`POST /mcp`) and stdio (`swarmail mcp`), up
  from twelve. New: `swarmail_wait_for_code`, `swarmail_wait_for_link`,
  `swarmail_create_inbox`, `swarmail_list_attachments`,
  `swarmail_get_attachment` and `swarmail_get_deliverability_report`. No
  v0.1.0 tool was renamed or removed.
- **Protocol revision negotiation** (0079, 0080, 0101, 0104): `2025-03-26`,
  `2025-06-18` and `2025-11-25`. A supported requested revision is returned
  as asked; an unsupported string receives `2025-11-25` so the client can
  decide; an omitted version keeps `2025-03-26`; a non-string version is
  `-32602`. HTTP stays stateless: the `MCP-Protocol-Version` header selects
  the revision per request, a missing header selects `2025-03-26`, and an
  invalid, duplicate or unsupported header is refused (HTTP 400, `-32600`)
  before any effect. JSON-RPC batches are available only under `2025-03-26`;
  both modern revisions refuse every array before a member runs. The stdio
  bridge relays `initialize` and sends the revision it returned as the header
  on every later request.
  Version negotiation is claimed; full revision conformance is not, and the
  operator-chosen deviations C1–C6 are registered in
  [`specs/mcp-version-negotiation/reconciliation.md`](../../specs/mcp-version-negotiation/reconciliation.md).
- **Structured outputs** (0082, 0105): under `2025-06-18` and `2025-11-25`
  every tool declares an object-root `outputSchema`, and a successful result
  carries `structuredContent` beside the same JSON in its text block. Modern
  descriptors add `readOnlyHint` / `destructiveHint`. `2025-03-26` results
  are byte-for-byte what they were.
- **Compact email view and field projections** (0108): on the modern
  revisions `swarmail_search_emails` and `swarmail_get_latest_email` answer a
  compact view by default — `id`, `from`, `to`, `subject`, `received_ms`, a
  200-character `snippet`, `codes`, `anchors` (`url`, `anchor_text`) and
  `attachments` — and the four reads (search, latest, get, wait) take
  `fields` to project exactly the members you name. REST gains
  `GET /api/v1/inboxes/{inbox}/messages?view=compact`; every other REST
  answer is unchanged.

## Test layer — waiting on the right mail

- **Focused waits** (0094, 0097): `swarmail_wait_for_code` answers the
  newest eligible mail's code as `selected`, `ambiguous` (several codes in
  that mail — never resolved from older mail) or `timed_out`, with
  provenance. `swarmail_wait_for_link` matches `anchor_text`, `host` and
  `path` regex searches on the same link occurrence and selects exactly one
  distinct URL, or answers `ambiguous` with every candidate. Link anchor
  text, `rel` and source part are now recorded at ingest; email reads, feeds
  and webhooks keep their v0.1.0 `links` shape, and mail stored earlier keeps
  its links with a `null` label.
- **Near misses on a timeout** (0111): a timed-out `swarmail_wait_for_email`,
  `swarmail_wait_for_code` or `swarmail_wait_for_link` over a non-empty inbox
  carries `near_misses` — up to ten recent arrivals, each with the filters it
  `missed`, the `nearest_subject` and `last_arrival_ms` — read once from the
  wait's own inbox, on every revision. An empty-inbox timeout keeps its
  exact bytes. REST `await` is unchanged.
- **Attachments and ICS** (0110): `swarmail_list_attachments` and
  `swarmail_get_attachment` answer from what ingest recorded at `250`:
  filename, content type, decoded size and SHA-256 per part, up to 250
  entries, and the bytes of parts that fit a 1 MiB per-mail budget (a larger
  part is listed with `stored: false` and stays readable through
  `GET /api/v1/messages/{id}/raw`). A calendar part carries `dtstart`,
  `dtend` (with `TZID`), `summary` and `uid` from its first `VEVENT`,
  verbatim, with no timezone resolution. Both tools are MCP-only.
- **Recipient inbox routing** (0112): `swarmail serve --route-domain
  swarmail.test` (or `SWARMAIL_ROUTE_DOMAIN`) stores a recipient
  `<local>@<label>.swarmail.test` in inbox `<label>`, ahead of the AUTH
  username — so one application login can serve many agents. A recipient
  under the domain that names no inbox is refused `550 5.1.3`; a second
  routed inbox in one transaction is deferred `452 4.5.3`.
  `swarmail_create_inbox` mints a private inbox and its address; on a server
  without the flag it answers an error naming the flag. Without the flag the
  server behaves exactly as before (0004).
- **Deliverability reports** (0085, 0089, 0106, 0107):
  `GET /api/v1/messages/{id}/deliverability` and
  `swarmail_get_deliverability_report` compute a versioned report
  (`swarmail-html/3`) lazily from the stored bytes, off the SMTP path, with
  findings located by header, MIME part or link. It holds the Gmail/Yahoo
  bulk-sender checklist (one-click unsubscribe, `Message-ID`, `Date`, a
  plain-text part) and seven HTML client-compatibility heuristics (CSS
  `position`, `display:flex`, `<video>`, missing `alt`, image-only HTML,
  Gmail clipping above 102 KiB, tracking pixels), each citing its published
  source. REST `assert` / `await` and `swarmail_wait_for_email` take
  `no_findings_at_or_above`. Empty findings certify nothing (see Known
  limits).

## Client fixtures

`clients/playwright` (`@swarmail/playwright`) and `clients/pytest`
(`pytest-swarmail`) give each test a fresh inbox and `waitForCode` /
`waitForLink` (`wait_for_code` / `wait_for_link`) that wake on the server's
long-poll and raise an explicit ambiguity error instead of picking the first
candidate (0113). They have no runtime dependencies, carry the server's
version (this release: 0.2.0, checked under `cargo test`), and CI runs their
example suites against the built binary. They are **not published** to npm
or PyPI: publishing is a separate operator act.

## Evals

- **The harness** (`evals/`, 0055, 0063, 0071, 0073, 0075, 0076): a fixture
  application, a v2 catalogue of 16 tasks with oracle solutions, an
  agent-agnostic trial runner, `matrix` and `report`, and wrappers for
  Claude Code, Codex and dsh (0083). Every task passes with the scripted
  `oracle` and fails with the do-nothing `null` before any agent is measured.
  Rows record the commit, binary digests, harness revision, agent argv
  digest and seed (0063); trials run in a closed environment with safe
  diagnostics (0075); named traps invalidate a trial (0071).
- **The published baseline**
  ([`docs/evals/baseline-2026-11-01.md`](../evals/baseline-2026-11-01.md)):
  395 of 400 paid trials passed on main `a4f552d` — five models, 16 tasks,
  five trials each, after 16/16 oracle passes and 16/16 null failures. All
  five failures are early `gave_up` exits by one model. The suite is
  saturated at this difficulty (see Known limits).
- **Trial isolation, prepared** (0115): a hidden `trial --isolated` flag runs
  the whole trial — runner, Swarmail, fixture and agents — inside one
  bubblewrap sandbox (user, PID, network and IPC namespaces, private `/tmp`,
  HOME and `/proc`), or refuses by name before anything starts, with no
  unisolated fallback. It is not activated: trials stay sequential (0076)
  and rows stay `unconfined`.
- **The fair mail comparison** (0091, 0092, 0093): pinned Mailpit and
  MailHog artifacts, a frozen protocol, a wire driver and
  `scripts/compare-mail.sh`. One collection is admitted as raw measurement
  only; no comparison result is claimed
  ([`docs/evals/README.md`](../evals/README.md)).

## Hardening since v0.1.0

Recorded after the v0.1.0 tag in that release's "Unreleased" sections and
shipped here: extraction fidelity (0040), the webhook boundary (0041),
extraction and compat (0049) and the compat and validation sweep (0044).
Each still holds; since then the field-prefix refusals widened to quoted and
wrapped forms (0061), unknown query keys refuse on every native route
(0074), and positional seed and chaos bodies refuse (0070). Beyond those:

- **The store's mutation boundary**: one ordered commit before visibility,
  off the async workers, refusing with no trace on failure or once stopping;
  a failed commit answers SMTP `451` or REST `503`, never `250` (0012, 0014,
  0015, 0016, 0023, 0024).
- **Waits observe shutdown** and every wire bound refuses rather than
  clamps (0018, 0025); the awaits registry and its watchers are bounded and
  released with their inbox (0021).
- **SMTP and POP3 edges**: a bounded, byte-honest DATA path whose `/raw`
  serves the stored bytes (0022), complete DATA terminators and deliberate
  session transitions (0034), trickle and idle lifetimes (0036), POP3 size
  accounting (0037), `TCP_NODELAY` and verbatim identities (0046).
- **Sender-honest stored bodies** with no synthesis (0031), emptied inboxes
  removed everywhere (0032), and the store's memory exposure and parse-start
  timestamps stated (0038).
- **JSON-RPC**: concurrent stdio lines with batch replies preserved (0039),
  named JSON-RPC errors and closed arguments (0044), correlated RPC
  refusals (0047, 0062).
- **Metrics**: the in-flight HTTP gauge carries the decoded inbox name
  (0043, 0065); no v0.1.0 metric was renamed or removed.

The per-item user impact is under *Upgrading* below.

## Upgrading from v0.1.0

Check these if you ran the v0.1.0 binary or wrote a client against it. The
published `:0.1.0` image is not the tagged commit: it is the 2026-10-12
build of `main` (its exact commit is not recorded here), so its users may
already have some of the changes below — POP3, persistence, STARTTLS and the
shims landed between 2026-10-08 and 2026-10-09 — and not others, such as the
loopback plane (2026-10-16) and the `Origin` check (2026-10-18).

**Process, listeners and configuration**

- **Loopback by default** (0030). v0.1.0 bound SMTP and HTTP on `0.0.0.0`;
  every listener now binds `127.0.0.1` unless told otherwise. A host reached
  over the network sets `SWARMAIL_SMTP_LISTEN`, `SWARMAIL_POP3_LISTEN` and
  `SWARMAIL_HTTP_LISTEN` (or `--smtp-listen`, `--pop3-listen`,
  `--http-listen`) to `0.0.0.0:<port>`; the image and the chart already do.
- **`Host` and `Origin` are checked on every route** (0030, 0043). On a
  loopback bind a request whose `Host` is not a loopback spelling of the
  bound port, or whose `Origin` is not, is a `403` — a proxy, tunnel or port
  forward that rewrites `Host` is refused. Off loopback a present `Origin`
  must match the `Host`.
- **`serve` also binds POP3** on `127.0.0.1:1110`. There is no switch to
  turn it off; move it with `--pop3-listen` if the port is taken.
- **Sessions are capped** at 256 per SMTP and POP3 listener; the next is
  answered `421` (`--max-sessions` / `SWARMAIL_MAX_SESSIONS`, 0027). Idle
  sessions close after 5 minutes (SMTP) or 10 (POP3).
- **Signals and exits** (0027): `SIGTERM` and `SIGINT` start a graceful
  drain of up to 10 s and a second signal exits 70; a startup failure prints
  `swarmail: <reason>` and exits 1. Give containers `--stop-timeout 30`.
- **Logs:** `swarmail mcp` logs to stderr, never to its JSON-RPC stdout
  (0029 §4); `serve` emits ANSI colour only on a terminal.
- **New, off unless set:** `--data-file`, `--tls-cert` / `--tls-key`,
  `--tls-handshake-timeout-ms`, `--route-domain`, and the `gen-cert`
  subcommand. No flag or subcommand was renamed or removed.
- **Memory:** a stored mail may now also hold up to 1 MiB of decoded
  attachment bytes and its attachment labels, in memory and in the data
  file (0110).

**SMTP clients**

- **Stricter protocol** (0028, 0034, 0046): `MAIL FROM:<…>` and
  `RCPT TO:<…>` need their angle brackets; blank or control-bearing paths
  and unknown parameters are refused; a second `MAIL` inside an open
  transaction is `503`; DATA ends only on CRLF `.` CRLF (a bare-LF `.` line
  is payload); the 101st recipient is `452`; a command line over 4096 bytes
  is `500`.
- **One AUTH per connection** (0028): a second AUTH is `503` and changes
  nothing — Python's `smtplib` does not raise on it, so open a new
  connection per inbox. Undecodable or blank credentials are `501`, and the
  username is used verbatim (v0.1.0 trimmed it).
- **Chaos at `data` always fails the stage:** a rule with only `delay_ms`
  now answers `451 4.3.0 chaos` and stores nothing, where v0.1.0 delayed
  and stored.

**REST and webhooks**

- **`DELETE /api/v1/messages` no longer wipes everything** (0011). It takes
  a non-empty `{"ids": [...]}` body or answers `400`; the explicit wipe is
  `DELETE /api/v1/delete-all`.
- **The email JSON changed** in REST answers, webhook payloads and full MCP
  emails: `session` is gone; `envelope_from` is always present (possibly
  `null`); `message_id`, `in_reply_to` and `references` appear when the mail
  has them. `links` and `codes` keep their v0.1.0 string-array shape.
  `/api/v1/messages/{id}/raw` serves the exact received bytes as
  `message/rfc822`.
- **Closed inputs** (0025, 0029, 0044, 0048, 0070, 0074): an unknown query
  key on a native route is a `400`; `limit` and `count` above 250 and an
  `await` `timeout_ms` above 60000 are refused rather than clamped; `count`
  no longer takes `limit` / `offset`, nor `assert` `timeout_ms`; seed and
  chaos bodies must be JSON objects with known, non-null keys; a seed
  refuses CR, LF or NUL in its envelope fields and keeps `html` verbatim;
  chaos `probability` is 0–100, `error` one 4xx/5xx line, `delay_ms` at most
  300000. Seed and webhook body errors are `400` (they were `422`); chaos
  body errors stay `422`. A blank or control-bearing inbox name is a `400`.
- **`GET /api/v1/inboxes` is paged** (`limit` default 100, at most 250,
  `offset`); an inbox emptied by deletes leaves the listing (0032).
- **`assert?count=0` means exactly zero** (0010); v0.1.0 raised it to one.
- **`/healthz` can answer `503`** (`degraded` or `stopping`, 0027), and a
  parked `await` answers `503` when the server stops (0018).
- **Webhooks** accept `https://` targets. `PUT` validates the whole list and
  refuses with `400`, keeping the previous one, when a URL is not
  `http(s)` with a host, an `inbox` filter is invalid, a `ca_pem`
  certificate does not load, or a secret is not a valid header value
  (padded and control-bearing secrets that v0.1.0 accepted). `GET` and the
  `PUT` echo withhold `secret`, strip URL credentials and echo only the
  certificates of a `ca_pem`; private-key blocks are accepted beside them
  but never echoed (0041, 0048, 0067). Deliveries ignore `HTTP_PROXY`,
  `HTTPS_PROXY` and `ALL_PROXY`.
- **Shim users** (the `:0.1.0` image and later builds): see the
  compat and validation sweep in [`v0.1.0.md`](v0.1.0.md) —
  `messages_unread_count` is now `messages_unread`, the senders follow the
  envelope, and quoted, negated or wrapped field prefixes refuse by name
  (0044, 0049, 0061).

**MCP clients**

- **The revision is negotiated** (0079). v0.1.0 echoed whatever
  `protocolVersion` a client sent and always behaved as `2025-03-26`. A
  client that asks for `2025-06-18` or `2025-11-25` now gets that
  revision's behaviour: JSON-RPC batches are refused, results carry
  `structuredContent`, and `swarmail_search_emails` /
  `swarmail_get_latest_email` answer the compact view, without `text` or
  `html`, unless `fields` names them (0082, 0108). An unsupported version
  string now receives `2025-11-25`. Over HTTP each request needs
  `MCP-Protocol-Version`; without it the request is served as `2025-03-26`.
- **Discovery order moved:** `swarmail_get_deliverability_report` is second
  in `tools/list`, after `swarmail_search_emails`. Address tools by name.
- **Arguments are closed:** an unknown argument key or a wrong type is
  `-32602`; `swarmail_set_chaos` requires `probability`; `limit` and
  `count` are at most 250, and a `timeout_ms` above 60000 is refused.
- **Results that changed:** `swarmail_search_emails`' `total` is now the
  full match count, not the page length, and its default `limit` is 100
  (was 50); `swarmail_wait_for_email` results carry `total`;
  `swarmail_get_latest_email` on an empty inbox, and a missing id for
  `swarmail_get_email` or the extract tools, answer an `isError` result
  instead of `{"emails": []}` or a `-32601` error.
- **Errors use their JSON-RPC codes** (`-32700`, `-32600`, `-32601`,
  `-32602`) where v0.1.0 answered `-32601` for everything; `initialize` no
  longer advertises `resources`.
- **Limits:** a request body over 2 MiB is refused, tool calls share a
  budget of 1024 per second per server, and the stdio bridge caps a
  response at 10 MiB (it no longer cuts a long wait off after 10 s).

**Docker and Helm**

- The image declares `VOLUME /data` owned by uid 65532 and `STOPSIGNAL
  SIGTERM`, and ships an empty `/tmp` the data-file lock needs (0051 §3, #203).
  Run it with `--rm --stop-timeout 30`; a volume an older image created is
  root-owned and needs `chown 65532:65532` once.
- The chart (published only as OCI `0.1.0` before this release) now sets
  the three `0.0.0.0` binds in `config`, always rolls out with `Recreate`,
  refuses `replicaCount` above 1, and adds `startupProbe`, `tls.*` and
  `networkPolicy.ingressPeers` (0008, 0026).

**Data files**

The v0.1.0 binary had no data file, so there is nothing to migrate from
it. A data file written by a later build — the `:0.1.0` image included —
gains nullable columns on first open and is never backfilled: its older mail keeps its stored fields, has
no link labels and lists its attachments as unknown (0040, 0094, 0110).

## Known limits

- **Eval trials are sequential.** One trial per uid runs at a time (0076);
  `--concurrency` other than 1 refuses. Trial isolation (0115) is prepared,
  not activated: it needs Linux and `/usr/bin/bwrap` 0.11.1 or later (stock
  Ubuntu 24.04 ships 0.9.0, which it refuses) with a host policy that lets
  bubblewrap create user, PID, network and IPC namespaces; macOS refuses by
  name. Until the operator rules on provider egress, `--isolated` refuses
  every wrapper profile, so no real model runs isolated, and its live
  criteria have not all passed.
- **Tokens per success are not yet measured.** Baseline rows carry no token,
  turn or cost field, and no transcripts were captured. The glm-dashscope
  cells (80 slots) and a pre-epic starting point were not run, and
  `swarmail-evals baseline` still refuses paid admission — the baseline ran
  as one `matrix` per task × model.
- **The baseline suite is saturated.** Four of five models scored 80/80, so
  its failure taxonomy cannot rank work; a harder tier is in progress
  (#309).
- **MCP client compatibility receipts are still owed.** Version negotiation
  is claimed, full revision conformance is not; recorded results from Claude
  Code, Codex, MCP Inspector and Claude Desktop remain operator-owned
  obligations under 0079. The agent setup guide's snippets are proved
  against the binary, not loaded by those clients, and the guide has not been
  run against a real model.
- **Known-flaky eval tests are tracked in #302**
  (`cleanup_observation_error_and_forced_expiry_fail_with_live_owned_processes`).
- **Deliverability reports do not verify authentication.** DMARC policy,
  From alignment and aligned DKIM/SPF are reported as error-level
  `*.not_evaluated.v1` findings until trusted observations exist (#253,
  #255), so in production `no_findings_at_or_above` qualifies no message at
  any threshold. The HTML rules are dated heuristics, not client
  measurements; empty findings certify neither compatibility nor
  deliverability.
- **Client packages are unpublished.** Neither npm nor PyPI carries them,
  their JavaScript/Python coverage is not measured and the packaged forms are
  unproved (0113).
- **The fair mail comparison has no result.** Only raw measurement is
  admitted ([`docs/evals/README.md`](../evals/README.md)).
- **Not on crates.io.** The crate is publish-ready; nothing uploads it.
- **No MCP resources or subscriptions.** They were evaluated and not
  shipped (0114); `resources/*` calls answer `-32601`.
- **The release receipt is external.** The first guarded GHCR
  404-then-publish receipt (#186 finding 18.5) is collected from this tag's
  release run, not proved by local fixtures; image and chart publication are
  not one transaction (0019, 0051).
