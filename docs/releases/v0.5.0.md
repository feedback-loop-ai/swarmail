# v0.5.0 — SPF, DMARC and ARC in the deliverability report, and a run console

Fifth release, prepared 2026-11-17 on `main` at `9ac77db` (#370). It
carries everything merged since v0.4.0 (`c95386e`, 2026-11-06): SPF for the
observed SMTP envelope and DMARC policy and alignment, a weight on every
finding and a total on every report, and ARC chain validation with a typed
`arc` report member, which completes the authentication epic (#251); the
web UI reworked as a run console, with one read-only projection route and two
read-only fields to feed it; the container image for `linux/arm64` as well
as `linux/amd64`; rusqlite 0.41 for RUSTSEC-2026-0459; an eval task that
repairs mail from the report; the published results of the paid
agent-suite comparison, the hard and expert tiers' paid run and a
throughput collection; and the comparison driver's first slice of protocol
v4, cost to operate under an enforced cgroup v2 budget, which measures other
servers and changes nothing in Swarmail itself.

The deliverability report is again the one surface that changes for every
caller: its bytes, its `rule_set_id`, its schema and its key set move (see
*Upgrading*). The other wire changes are additive: one new read-only route,
two new members on `/healthz` and one on the inbox list, and a header on the
UI pages. The data file gains two nullable columns, added on open.

The frozen guarantees are unchanged: an SMTP `250` means the mail is
queryable (0001), `await` subscribes before it checks (0002), pruning is
oldest-only (0003), and extraction happens at ingest (0005). SPF, DMARC and
ARC run in the lazy report evaluator after the `250`; the observed client
address and HELO name are captured on the SMTP path and committed with the
row, before the `250`; nothing new runs in `Store::insert`. Every decision a
product change below ships under is accepted, and one record is still
proposed. The operator accepted 0126 (SPF and DMARC) on 2026-11-07, "accept
all three", for its three holds: an amendment of accepted 0120 (the optional
`spf_client_ip` and the non-TXT and `np=` answers), SPF's 20-second
monotonic lookup timer as a further amendment of accepted 0085 §8, and a
reading of accepted 0089 §5. 0122 §2 (the weight and total), which v0.4.0
shipped as accepted but not built, is now built (#344). The operator
accepted 0129 (the agent-suite comparison) and 0130 (eight comparison
targets) on 2026-11-08, and on 2026-11-16 accepted 0132 (comparison protocol
v4, "Accept all as proposed"; story A of four is built here, #370), both holds of 0133 (ARC) and 0134 (the UI
projection, "approved"). 0126, 0133 and 0134 were each accepted before their
PR merged. **0131 (deliverability for agents) is still proposed**: it holds
nothing, so #345 landed under 0045 §8 as compatible work; on acceptance it
amends the eval harness specification's tier list. The Zlib licence
allowance came back by the operator's ruling of 2026-11-10 ("Upgrade + allow
Zlib"), which is not a decision record.

## Deliverability

The report at `GET /api/v1/messages/{id}/deliverability` and MCP
`swarmail_get_deliverability_report` gains SPF, DMARC and ARC, and every
report gains a weight per finding, a total and an `arc` member. All of it is
computed lazily from the stored bytes, off the SMTP path, and cached as
before. The report's `rule_set_id` moves from `swarmail-html/6` to
`swarmail-html/9`. `swarmail-html/7` (SPF and DMARC) and `swarmail-html/8`
(weight and total) were the ids on `main` between the merges; neither
shipped in a release. See the
[deliverability guide](../guide/deliverability.md) for every rule, bound and
known gap.

- **SPF and DMARC** (0126, #343, closes #255). SPF is evaluated for the SMTP
  envelope, and DMARC for the root `From`, with relaxed and strict alignment
  of SPF and of the DKIM verdicts v0.4.0 added. Each outcome is reported the
  way Authentication-Results names it. The crate is `mail-auth` `=0.14.0`, as
  for DKIM; no package, feature or licence was added.
  - **The observed envelope.** The SMTP session now records the TCP peer and
    the argument of the last `HELO`/`EHLO` in the stored row, before the one
    synchronous insert, so they ride the same commit as the `250`. They are
    never read from a header. REST-seeded mail and rows stored before this
    release hold none and are never backfilled. Neither appears in any
    `Email` serialization, feed frame or webhook payload; the run console's
    projection route (below) is their one read.
  - **The identity and the address.** One `check_host` per message: the MAIL
    FROM domain, or the HELO name for a null reverse path. SPF sees the
    socket's address, so a test over loopback declares `ip4:127.0.0.1` in its
    record, or declares the new optional `spf_client_ip` in the DNS policy
    (the server file or `PUT /api/v1/inboxes/{inbox}/dns`), which is applied
    to every peer and echoed in `dns.policy` only when declared.
  - **TXT only.** The declared policy is a TXT map, so the `a`, `mx`, `ptr`
    and `exists` mechanisms and the `%{p}` macro are not evaluated: they give
    `spf.unsupported_mechanism.v1`, never a failure. RFC 7208's limit of ten
    DNS-querying terms is enforced; one evaluation looks up at most twelve
    names and a DMARC tree walk at most eight.
  - **DMARC.** The RFC 9989 tree walk asks for `_dmarc.<name>` from the
    Author Domain upward. The organizational domain and the public suffix
    are decided by the declared records alone (a declared `psd=y` marks a
    public suffix); no public suffix list is fetched, checked in or compiled
    in. A failure carries the applied policy in its id
    (`dmarc.fail.none.v1`, `.quarantine.v1`, `.reject.v1`); `pct=` is
    ignored, as RFC 9989 has no such tag.
  - **Sixteen findings**, eight `spf.*` and eight `dmarc.*`, each with a
    passing and a failing fixture. A pass emits nothing. Every one is an
    error except `spf.not_evaluated.v1` (info), which marks mail with no
    observed peer or sender, such as REST-seeded mail.
  - **The bulk checklist reads real evidence.** The six facts behind
    `bulk.dmarc_presence`, `bulk.from_alignment` and
    `bulk.authenticated_sender` are now outputs of this evaluation, where
    v0.4.0 left them unknown and emitted their error-level
    `*.not_evaluated.v1` findings for every message.
  - **The second exception to byte-identical reports.** SPF's evaluation
    starts a monotonic timer inside the crate and refuses a DNS-querying
    term once 20 seconds have passed on it. Only a process descheduled for 20
    seconds inside one evaluation sees it, and the verdict is then
    `spf.permerror.v1`, fail-closed and never a pass. The operator accepted
    this on 2026-11-07 (0126 §8). DMARC reads no clock; the crate's `ra=`
    sampling and `%{t}` are unreachable.

- **A weight per finding and a report total** (0122 §2, #344, closes #337).
  Every finding gains `weight` as its last key and every report gains
  `total` as its last key; the existing key prefixes are byte-identical. The
  weight comes from severity alone, for every rule family: info 1, warning
  3, error 10. Any id containing `.not_evaluated.` and `demo.marker.v1`
  weigh 0. `total` is the sum after sorting and de-duplication, computed
  inside the report's byte bound, so a cached and a fresh report are
  byte-identical; it is at most 2,560, and an overflow fails the report
  rather than wrapping. **Predicates ignore both**: `no_findings_at_or_above`
  still decides on severity (and on a `temp_fail` lookup) alone, so a total
  of 0 is not "clean" and a large total is not "dirty". No edge (REST, MCP,
  the UI) computes a score.

- **ARC chain validation** (0133, #364, closes #256, the last story of epic
  #251). The ARC chain (RFC 8617) of a stored message is validated on
  `mail-auth`'s `arc` feature, which adds no package.
  - **The `arc` member.** Every report carries
    `"arc":{"state","sets","failing_instance","reason"}` after `dns` and
    before `total`. `state` is `none`, `pass`, `fail` or `not_evaluated`;
    `failing_instance` is the `i=` that broke the chain, only with `fail`;
    `reason` is the rule id of the report's one `arc.*` finding. A pass and a
    message with no ARC field both emit no finding, so **a test that asserts
    a forwarder's chain validates reads `arc.state == "pass"`**, not the
    absence of `arc.*` findings.
  - **What is verified.** The three field families with instances 1 to 50,
    the structure (complete sets, consecutive instances, `cv=`), the newest
    `ARC-Message-Signature`'s body hash and signature, and every seal, newest
    first, under `rsa-sha256` and `ed25519-sha256`. The contents of an
    `ARC-Authentication-Results` field are never read, and no fact, DMARC
    result or other finding changes with the chain: `arc=pass` says the chain
    validated, not that the sender is authentic.
  - **Keys come from the declared DNS map only**, at `<s>._domainkey.<d>` of
    each hop; a chain asks at most 51 names. The failing seal is named
    exactly from the number of keys the verifier asked for.
  - **Time is the receipt time.** An `x=` on the newest
    `ARC-Message-Signature` at or before the receipt second is
    `arc.signature_expired.v1`; an `x=` after it is `arc.not_evaluated.v1`,
    because only the wall clock could judge it. The crate reads the wall
    clock once inside its verifier, but the chain reaches it only when that
    field has no `x=`, so the value is never compared; the operator accepted
    that reading of 0085 §8 on 2026-11-16 (0133 §5).
  - **Thirteen `arc.*` findings**, at most one per report, every one an
    error; `arc.not_evaluated.v1` weighs 0.
  - **A shared bound.** DKIM's non-strict re-parse for an `l=` signature
    would also hash every `ARC-Message-Signature` with `l=`, so the `l=`
    fields of both kinds share DKIM's bound of 16.

- **Deliverability for agents** (proposed 0131, #345, closes #261). The
  structured MCP output #261 asked for had already shipped under accepted
  0105, so no report byte, schema or tool changes; two test-only guards pin
  it (the served description names the current `rule_set_id`, and modern
  `structuredContent` equals the text block and REST on a report with a
  populated `dns`). The guide gains a *For agents* section and `llms.txt` a
  paragraph; `tests/fixtures/deliverability-agent/` publishes a failing and
  a fixed `.eml`. The eval task is under *Evals* below.

## Web UI — the run console

- **One console instead of three pages** (0134, #365, closes #355; #369).
  `/`, `/ui/inbox/{inbox}` and `/ui/inbox/{inbox}/thread/{key}` serve one
  page with three panes (inboxes, live stream, reader) under a status bar,
  ported from the prototype the operator accepted on 2026-11-16. No UI route
  was added or removed.
  - The status bar shows each listener's state from `/healthz` (a `503` that
    names a degraded listener is shown by name), the lifetime accepted and
    dropped counts, the chaos state read-only, and the live feed's state.
  - The reader shows the envelope, codes and links, attachments and calendar
    invites, the SMTP client address and HELO name, and the deliverability
    report with an authentication row. Its ARC chip reads the report's
    `arc.state` (#369): `pass` green, `fail` red with the failing `i=`,
    `none` neutral, `not_evaluated` info. Report requests run one at a time,
    newest and selected mail first, so the console holds at most one of the
    four analysis slots.
  - Mail links are text with a copy control, never a mail-controlled `href`.
    The one write is a two-step "Clear inbox", on the existing
    `DELETE /api/v1/inboxes/{inbox}/messages`. Light and dark follow
    `prefers-color-scheme`; there is no toggle, no sample mail and no chaos
    switch.
  - `GET /ui/message/{id}` keeps its markup: server-rendered, escaped, no
    script. It takes the new stylesheet.
  - The UI routes now answer `X-Frame-Options: DENY`, because the console
    carries a destructive control and its CSP, a `<meta>` tag, cannot carry
    `frame-ancestors`.

- **A read-only projection route** (0134 §1–§5).
  `GET /api/v1/messages/{id}/projection` returns exactly
  `{id, smtp_client_ip, smtp_helo, links, attachments}`. `links` and
  `attachments` are `null` for rows from before ingest kept them, else
  `{total, items}` with at most 250 items (0108's cap): a link is
  `{url, anchor_text, source}` and an attachment
  `{filename, content_type, size, ics}`. It serves stored fields only: no
  bytes, no hash, no `rel`, no re-parse of `raw`. An unknown id is `404`, any
  query key `400`, another method `405`. It amends 0110 §7, 0094 §2 and 0126
  §2 by dated addendum, for this one read; every `Email` serialization keeps
  its bytes.

- **`/healthz` counters and the inbox list's last mail** (0134 §6–§7). The
  `200 ok` and `503 degraded` bodies gain `emails_inserted_total` and
  `emails_dropped_total`, the store's lifetime counters (the values
  `/metrics` already exposed; "dropped" is mail evicted by the per-inbox cap,
  not chaos refusals). The `503 stopping` body is unchanged. Every item of
  `GET /api/v1/inboxes` gains `last_received_ms`, the server's stamp of the
  newest retained mail in that inbox, never its `Date` header.

## Container image

- **`linux/arm64` as well as `linux/amd64`** (#354, #366). CI builds each
  platform natively (`ubuntu-latest` and `ubuntu-24.04-arm`, no QEMU),
  pushes each by digest, smokes that exact digest on its own platform, and
  writes the same tags as before as one multi-platform index; the tag step
  refuses an index that does not name both platforms. #366 restored the tag
  job's admission on `main`, where the tag-only rate proof is skipped by
  design and #354's split had left `:main` amd64-only. `:main` has carried
  both platforms since. The Dockerfile did not change: the pinned builder is
  already a multi-architecture index. v0.5.0 is the first release tag
  published this way; `:0.4.0` and earlier stay `linux/amd64` only.

## Dependencies and security

- **rusqlite 0.41 for RUSTSEC-2026-0459** (#353). The C SQLite bundled by
  `libsqlite3-sys` 0.30.1 could return uninitialized page-cache bytes when
  opening a crafted database with a mismatched `-wal` file. Swarmail's
  exposure was low (an attacker must plant both files where it opens its
  data file), but the RustSec audit failed every PR. rusqlite 0.41.1 bundles
  `libsqlite3-sys` 0.39.1 (SQLite 3.54.1); no source change was needed.
  `foldhash` 0.2.0 (Zlib only) comes in through hashbrown 0.17, so Zlib is
  back on the licence allowlist, with the reason in `deny.toml` and the house
  rules. `hashlink` moves to 0.12.2; `ahash` and `version_check` leave the
  tree.
- ARC uses `mail-auth`'s `arc` feature, which adds no package; SPF and DMARC
  add nothing. `native-tls` stays absent.

- **Eight comparison targets, frozen, not collected** (0130, #346, closes

- **A throughput collection, published as raw measurement** (#356, part of

- **Comparison protocol v4, story A: cost to operate under an enforced
  budget** (0132, #358, #370, closes #359; part of #349 and #351). Accepted
  0132 combines cost to operate, per-operation API latency, `wait-best` and
  a reference test suite; #370 builds the first of those and the plumbing
  under all of them. It is a measurement driver in `benches/mail_compare`
  and `scripts/compare-mail.sh`: `src/` is untouched, and nothing on the
  wire, the command line, the image or the chart changes.
  - **Protocol v4 and source lock v5**, as drafts
    ([`draft/protocol.v4.json`](../evals/draft/protocol.v4.json),
    [`draft/sources.lock.v5.json`](../evals/draft/sources.lock.v5.json)).
    Protocol v3 and lock v4 stay the active, frozen pair (their bytes are
    also kept under `history/`), and no v4 cell merges with a v2 or v3 cell.
  - **An enforced budget.** Every launch runs in its own driver-owned
    cgroup v2 leaf under a delegated `systemd-run --user --scope`: 2 CPUs
    (`cpu.max` and affinity to two physical cores), 2048 MiB (`memory.max`,
    no swap, `memory.oom.group`) and 4096 tasks. Each limit is written, read
    back and recorded; the child's cgroup and CPU set are read back after the
    spawn; a sampler reads the leaf every 100 ms; teardown writes
    `cgroup.kill` and removes the leaf. Off Linux, or without a delegated
    hierarchy with `cpu`, `memory` and `pids`, every launching v4 mode
    refuses; there is no unenforced fallback.
  - **Cost to operate** per target and cost profile (`cost-c1-reused`,
    `-c8-reused`, `-c32-reused`, `-c32-fresh`): visible mail per target
    CPU-second, peak `memory.current` with peak `anon` beside it, idle memory
    after readiness, and startup time and CPU, each a median with its range.
    A cell is ranked only at equal results, otherwise it names its
    shortfall. These are 0132 §5's headline figures; a figure that was not
    observed is `null`, never zero, and `mib_per_1k_retained` is published
    as owed until story B.
  - **New modes:** `mail_compare hold` (one target under the budget),

    installed tree's digest), `admit-v4 [--seal]` (recomputes every figure

    operator approved the `scripts/` change by accepting 0132.
  - **Proof.** The five kernel proofs (`v4_real_oom_at_two_gib`,
    `v4_real_cpu_held_within_two`, `v4_real_setsid_escapee_removed`,
    `v4_real_hold_swarmail_under_budget`,
    `v4_real_cost_chunk_seals_and_admits`) need a delegated cgroup v2 scope,
    so they are `#[ignore]`d in CI. The dispatcher ran them one at a time on
    its host at the merged head `886eb06`, with the load before and after,
    and all five passed (posted on #370). The operator ruled the merge on
    2026-11-17 under 0102. Six Linux-only tests (bind ownership through
    `/proc`, cgroup v2 detection) are ignored on macOS, with the reason.
  - **Not in this release:** stories B (per-operation API latency, #360), C
    (`wait-best`, #361) and D (the reference test suite, #362), all open; the
    v4 freeze and collection (story E), which is the operator's; and any

## Upgrading from v0.4.0

The deliverability report changes for every caller. The other wire changes
are additive; nothing was renamed or removed on the wire, the command line,
the image or the chart. Checked against the `v0.4.0` tag's code:

- **Report bytes change.** Every report's `rule_set_id` is
  `swarmail-html/9` (was `swarmail-html/6`). Every finding ends with
  `weight`; every report carries `arc` after `dns` and ends with `total`, so
  a REST report reads `rule_set_id, findings, dns, arc, total`. Mail over
  SMTP now gets `spf.*` and `dmarc.*` findings, and a signed or forwarded
  message can get an `arc.*` one. A test that pins a whole report, its
  `rule_set_id` or a finding count must be updated.
- **Report schemas are closed and gain required members.** OpenAPI's
  `DeliverabilityReport` and `DeliverabilityFinding` and the MCP tool's
  `outputSchema` (MCP `2025-06-18` and `2025-11-25`) require `arc`, `total`
  and `weight`. A client that validates against the v0.4.0 schema rejects a
  v0.5.0 report; take the new schema from `/openapi.json` or `tools/list`.
  MCP serializes with sorted keys, where `arc` sorts first and `weight` and
  `total` last.
- **Report predicates.** `no_findings_at_or_above` still reads severity
  only. In v0.4.0 every message carried error-level `bulk.*.not_evaluated.v1`
  findings and none qualified at any threshold. Now the facts are evaluated:
  a message can qualify when its declared records make SPF, DKIM and DMARC
  pass and its other findings sit below the threshold. Without declared
  records, SMTP mail gets `spf.none.v1` and `dmarc.none.v1`, both errors,
  and still qualifies at no threshold.
- **A report near the byte bound can now fail.** `weight` and `total` count
  toward the 65,536-byte bound (about 11 to 12 bytes per finding, up to 14
  for the total), so a report that was just under it can now answer REST
  `503 deliverability analysis failed` or MCP `isError`.
- **DKIM's `l=` bound is shared with ARC.** A message with a DKIM `l=` field
  and more than 15 `ARC-Message-Signature` `l=` fields now gets
  `dkim.limits_exceeded.v1` and no other DKIM verdict.
- **The DNS policy** admits an optional `spf_client_ip`, in the server file
  and in `PUT /api/v1/inboxes/{inbox}/dns`; `dns.policy` echoes it only when
  declared, so existing declarations and their echoes are unchanged.
- **A new route:** `GET /api/v1/messages/{id}/projection`, behind the HTTP
  plane's Host/Origin guard like every route.
- **`/healthz` bodies grow.** `200 ok` and `503 degraded` gain
  `emails_inserted_total` and `emails_dropped_total`. Status codes, `status`
  values and the degraded names are unchanged, and the `503 stopping` body is
  still exactly `{"status":"stopping"}`. A probe that compares the whole body
  for equality breaks; the chart's probes read the status code only.
- **The inbox list** (`GET /api/v1/inboxes`) items gain
  `last_received_ms`. It can step back a few milliseconds when two mails are
  stored out of stamp order.
- **The UI pages** answer `X-Frame-Options: DENY`; embedding the console in
  another origin's frame no longer works. `GET /ui/message/{id}` keeps its
  markup. Switching inbox in the console is a page navigation.
- **Data files** gain two nullable columns, `smtp_client_ip` and
  `smtp_helo`, added on open: a v0.4.0 data file opens as it is, and its
  rows hold `NULL`, so their SPF is `spf.not_evaluated.v1` (info) and their
  projection shows `null`. Opening a v0.5.0 data file with v0.4.0 was not
  tested.
- **The image** is a multi-platform index for `linux/amd64` and
  `linux/arm64`; an arm64 host now pulls a native image instead of running
  amd64 under emulation. A pin by digest must take the index's digest or the
  platform's.
- **The MCP surface** is the same eighteen tools.
  `swarmail_get_deliverability_report`'s modern description and output
  schema name SPF, DMARC, ARC, `weight` and `total`; the `2025-03-26`
  descriptor keeps its historical text.
- **New flags:** none. The startup log line is unchanged.
- **Building from a checkout** bundles SQLite 3.54.1 through
  `libsqlite3-sys` 0.39.1.
- **Rust callers of the library** (the crate is not on crates.io):
  `deliverability::Finding` gained `weight`, `deliverability::Report` gained
  `arc` and `total` (with `ArcChain` and `ArcState` exported), and `Email`
  gained `smtp_client_ip` and `smtp_helo` (both `#[serde(skip)]`). Code that
  builds these with struct literals must add the fields.
- **Eval harness users:** `swarmail-evals tasks` lists 25 tasks, so a digest
  over the whole catalogue moves; the default-tier and default-plus-hard
  subsets are unchanged. `--tier deliverability` is new and optional.

## Known limits

- **No real DNS.** SPF, DMARC, DKIM and ARC read only the declared TXT map;
  `--dns-resolver real` is still refused. SPF's `a`, `mx`, `ptr` and
  `exists` mechanisms and `%{p}` are unsupported, never evaluated. There is
  no public suffix list: a test that needs one declares `psd=y`.
- **ARC needs every hop's key in the declared map**, or the chain fails
  with `arc.key_missing.v1`. A chain whose newest signature carries an `x=`
  after the receipt second is reported `not_evaluated`, not verified; how
  often real sealers set `x=` on that field was not measured. Trusted-sealer
  lists and sealing are not part of this release, and `arc=pass` is never
  read as sender authentication.
- **Two exceptions to byte-identical reports** remain: DKIM's wall-clock
  `x=` residual (0125 §8) and SPF's 20-second monotonic timer (0126 §8),
  each fail-closed. The compiled-in resolver is unreachable, not absent.
- **The weight is severity, not a score.** There is no per-rule table and no
  threshold on `total`; the rules are dated heuristics, and empty findings
  certify neither compatibility nor deliverability.
- **The run console** makes up to two serial requests per painted row, so a
  200-row view fills its severity chips progressively; the new-mail dot can
  miss a mail stored out of stamp order (the count and the stream cannot);
  links are copy-only. The `/healthz` counters are lifetime counts, not a
  live inbox count.
- **The multi-platform tag is unproved on a tag.** The two build legs and the
  index have run on `main`; the `v0.5.0` release run is the first tag to
  publish them, after the tag-only rate proof.
- **The deliverability tier has no paid run**, and 0131 is proposed. The
  expert tier's paid run separates models on one task (`otp-late`) only, by
  a test chosen after the data. Tokens per success and transcripts are not
  measured.
- **The comparison results are narrow.** The agent-suite comparison finds no
  significant gap between four servers on a saturated hard tier, with cost
  unavailable. The throughput collection is raw measurement with the caveats
  above, and the README quotes none of it. Protocol v4 is partly built:
  its cost-to-operate driver (story A) ships as a draft that cannot yet
  collect, and Swarmail's push wait (story C) is still unmeasured. The
  eight-target protocol v3 has not been collected.
- **The v4 driver needs Linux and a delegated cgroup v2 scope.** Its CPU
  budget is a ceiling, not a reservation, so a busy host can still change a
  cell; `memory.current` counts reclaimable page cache; an empty leaf does
  not prove that a same-uid process never left it. Its five kernel proofs
  run on the dispatcher's host, not in CI.
- **Eval trials are sequential** (0076), and trial isolation (0115) is
  prepared, not activated.
- Unchanged from v0.4.0: inbox DNS declarations are process-local; the
  reachability probe's lookup cannot be cancelled; parse admission has no
  knob; the MailSlurper shim is a global mailbox and the chart does not
  expose its port; implicit TLS is one mode per process and POP3 has no TLS;
  MCP client compatibility receipts are still owed (0079); the client
  packages are unpublished (0113); the crate is not on crates.io; there are
  no MCP resources or subscriptions (0114); and publication is not one
  transaction (0019, 0051).
