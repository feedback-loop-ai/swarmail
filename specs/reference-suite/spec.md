# Run the reference mail tests under concurrency

Issue #362 measures what happens when independent application tests share a mail server. An API latency measurement cannot tell a developer whether the right account was confirmed, another test consumed its mail, or cleanup disturbed an overlapping wait. The unit of success is a scored fixture trial. The unit of comparison is one suite on one freshly launched target.

The operator approved the flows, budget, recipient scheme, wait selection, cleanup and evidence in [decision 0132, especially §§4, 7–9, 11–12 and its acceptance note](../../docs/decisions/0132-mail-comparison-protocol-v4.md). This design implements story D under that authority. Collection, freeze and publication belong to story E.

## Acceptance Criteria

1. One `testexec` command validates and runs one (target, parallelism, repetition) coordinate. Each of repetitions 0–2 at parallelism 1, 8 or 32 has 100 planned trials, twenty each of otp-backlog, recipient-crowd, digest-lookalike, reset-login and magic-login. Before launch, the seed determines the common queue, immutable trial numbers and reproducible scenario inputs. Worker scheduling cannot change those inputs. Private fixture tokens remain private.
2. The launcher owns one fresh, digest-checked target under the §3 enforced budget and CPU layout. Each worker has a ready fixture before the first trial starts, claims one job at a time, and starts each claim with fresh private app state. An outstanding handler can only affect its original trial. Each flow uses the existing fixture trigger, scripted solution and app-state scorer. Every pass requires the expected state and successful cleanup under the declared policy.
3. Swarmail receives a unique SMTP AUTH inbox per trial. Shared stores use unpadded primary addresses test-100@suite.invalid through test-199@suite.invalid. All five crowd addresses belong to that trial. Before delivery the full sets must be pairwise disjoint under the target's mailbox rules. With a shared store, use the cited server filter where available, complete its pages, then use the shared client's exact match. Fetch and delete use the original mailbox and verified identity. Each source exposes only the oracle's requested subject, scope and count, preserving same-trial lookalikes.
4. Every target uses its cited story C wait-best. Swarmail awaits the required count in the trial inbox. MailHog establishes stream readiness, performs an authoritative scan, rescans on wake and reconnect, and uses the 1,000 ms backstop. The remaining launchable targets use the cited 100 ms poll. Already-present mail works on every route. Each scan uses the same documented client as story B. No cache, prefetch, private delivery index, oracle hints or automatic fallback may affect selection.
5. Record the narrowest documented cleanup policy before work starts. Clear the trial inbox on Swarmail. With delete-by-ID, recover and verify all owned IDs including decoys and leftovers after failure. With only global clear, clear per test at 1, or once after all workers settle at 8 and 32, outside the suite window. Record unavailable capabilities, failed mutations and uncertain late deliveries explicitly. A failed narrow operation cannot authorize a broader one. Where the cited delete-by-ID read spans other trials' mail (Mailpit cites no recipient filter, so its listing is store-wide), parallel workers can move it while it is read. The pager's refusal of that listing as incomplete stands. At parallelism above 1 the cleanup reads it again until one listing is complete, inside the trial's cleanup deadline. At 1, a moving listing fails at once. Only reads repeat.
6. From each claim there is one row and one outcome. Use pass for scored success, timeout for an exhausted test deadline, wrong_message for an incorrect selection, content or mail assertion, interference for a failure causally attributable to foreign mail or foreign cleanup, and harness for fixture, launcher or transport faults affecting the trial. Record causal evidence and cleanup separately if both fail. Count distinct other-trial messages returned by a target filter and dropped by exact match as foreign_seen per trial, including passing trials. Repeated sightings and same-trial decoys contribute no extra count. Missing mail alone cannot establish interference.
7. Stop claims by 540 s from first start. Each test's entire operation including per-test cleanup is bounded by the earlier of suite cutoff and 30 s from claim. Respect the enclosing chunk deadline including setup, cancellation and teardown. Account once for every planned ID as started or unstarted, retain partial rows, and report class counts with their denominators. Record suite wall time from first claim to last trial end, per-trial wall time, wait-call-to-return and signed ack_to_return from the observed final DATA 250 for the required mail. Missing observations are absent with a reason. Record §4 target CPU and sampled memory peak, lifetime peak separately, and client process CPU from rusage over the suite interval.
8. Retain coordinate, seed, policies, methods, windows, launch, limits, samples and teardown evidence sufficient to recompute the section report. Successful measurement requires scored work, complete accounting and proved cleanup including cgroup_removed. Target failure (including crash or OOM) keeps measured losses, exit 1. Infrastructure, interrupt or unproved teardown leaves an incomplete chunk, exit 2. Preserve documented blocked setup and MailSlurper §6.4 fill_not_reached when its actual fill evidence exists, recording count reached and blocked denominator. A generic setup error cannot establish that condition. Story D introduces no suite prefill requirement.
9. Discover two named, ignored Linux host proofs, one full bounded Swarmail coordinate at 1 and one Mailpit coordinate at 8. Both must refuse missing prerequisites by name, verify candidate or pinned bytes, check the scored rows, evidence and teardown, and run the resource-owning driver alone in its delegated scope. The dispatcher runs each alone and attaches its output before merge. Local acceptance covers discovery, refusal, scope placement and fast deterministic tests. Real execution stays open until supported by host evidence.
